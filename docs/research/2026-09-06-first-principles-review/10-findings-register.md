## A. Independently confirmed clusters

Where two or more reviewers, working separately, hit the same underlying problem. These are the highest-confidence items; each was also spot-checked against source during synthesis.

| Cluster | Findings | What it is | Status of evidence |
|---|---|---|---|
| **Unsorted policies `ScMap`** | PAR-F1, API-F4, SVC-F17, SEC-F10(b) | `rules.add()` and the constructor deploy path hand an insertion-ordered `Map` to the bindings; `Spec.nativeToScVal` does not sort; the host rejects unsorted maps. Fails for ≥2 policies depending on address order. Demo works around it with `localeCompare`, which is provably not host order. | Confirmed by probe against the checked-in spec (PAR) and by an executed strkey-vs-host order check (SVC). |
| **`CreateContract` rules unreachable** | SEC-F9, ARCH-F13, TEST-F1 | `extractCreateContractWasmHash` duck-types three XDR accessor names, two of which don't exist; the real V2 arm is `createContractV2HostFn`. | **UV `"preferred"` vs verifier `required`** | SEC-F4, PAR-F10, TEST-F3(c) | SDK requests `userVerification: "preferred"` in every path; the deployed verifier unconditionally requires the UV flag (`webauthn.rs:346`). A non-UV authenticator yields a wallet that can never sign. | Confirmed against contract source. |
| **Connection is passkey-only; birth is one-passkey-only** | API-F1, PAR-F4, SVC-F6, ARCH-F14 | `_contractId` is only ever set by a WebAuthn ceremony; `createWallet`/relayer proxy hard-code exactly one WebAuthn signer at birth. | **Multiple signing pipelines & the `multiSigners` split** | API-F2, API-F3, ARCH-F6, ARCH-F15, PAR-F5 | Five sign→resimulate→submit implementations reading auth entries from three places; `needsMultiSigner()` pushes routing to the consumer; ~7 "signer" concepts; `AuthDigestSigner` exported but unused; custom verifiers can be registered but never sign. | Confirmed by call-graph analysis. |
| **The indexer is required, and needn't be** | SVC-F10, SVC-F11, SVC-F12, PAR-F8, API-F10, ARCH-F21, SEC-F12 | Fresh-device connect needs a complete schema-2 response even with a known contract ID; `rules.list()` silently under-reports past id 8; the freshness gate is self-reported. | **`execute()` / `policies.add()` documented wrong** | PAR-F2, API-F5, API-F14 | `Val`-typed args must be pre-encoded `xdr.ScVal`; README and the managers' own JSDoc pass raw values and throw. Six ways to express "threshold = 2". | Confirmed by executed probe (PAR). |
| **Separate bindings package** | ARCH-F16, TEST-F17, SVC-F16 | `export * from "@stellar/stellar-sdk"`, `window.Buffer =` at import, `Buffer` in public types, ~470 lines of shell, drift check not in CI, generated types frozen as public API. | Confirmed. |
| **Four error models** | API-F8, ARCH-F9, ARCH-F10, PAR-F9 | 94 typed throws, 59 plain `Error` throws, 41 result-union returns, 5 `console.warn/error` call sites; dead error classes/codes; contract errors identified by doc-string match (works for 3 of 16 codes). | Counted by grep. |
| **stellar-sdk v16 re-implemented** | ARCH-F4, ARCH-F5, ARCH-F20, TEST-F13 | Five hand-rolled `authorizeEntry` equivalents, three read-only simulation builders, hand ScVal codecs next to a generated `Spec`; stellar-sdk listed as both dependency and unbounded peer. | **Relayer is trusted without confirmation** | SEC-F3, SVC-F7, SVC-F9 | Non-deploy submissions accept any relayer-returned hash; no idempotency key; timed-out deploys strand the wallet as "occupied"; two hand-maintained wire shapes with no cross-boundary test. | Confirmed. |
| **Browser relayer path broken as committed** | SVC-F1, SVC-F2 | Hand-rolled CORS allows only `Content-Type`; SDK always sends `X-Client-Name`/`X-Client-Version` → preflight fails. Whether the *deployed* worker predates commit `f190326` is an open question. |
| **Config sprawl / addresses in six places** | API-F6, SVC-F19 | 24 config options, 8 of them per-network constants the SDK already pins; deployed addresses hand-copied into six files and present in `src/` nowhere. | Confirmed. |

| **Address derivation doesn't commit to the constructor** | SEC-F2, SEC-F10(a), SVC-F6, SVC-F10 | `salt = sha256(credentialId)` with a public deployer seed → anyone can squat a derived address with their own constructor; ~400 lines of provenance verification compensate; per-call `policies` break fresh-device recovery. | Confirmed against `utils.ts:165-183`. ## C. Checked and OK

Not everything is a finding. The security review explicitly verified and cleared the following (full list in [02-security.md § Checked and OK](02-security.md)): the auth digest is byte-identical to `do_check_auth`; every signer type signs only the digest; delegated nesting matches `require_auth_for_args`; the WebAuthn challenge matches `validate_challenge`; DER→compact is bounds-checked with low-S and `[1, n)` range checks; `compareScVal` matches the host's `Compare` impls (independently verified against `rs-soroban-env` by the parity review); `AuthPayload`/`Signer` decoders check every discriminant; nonces and challenges are CSPRNG; re-simulation cannot swap signed entries; the deploy auth entry is validated against the operation; the connect path is fail-closed against a hostile indexer; stored sessions and credentials contain only public data; no secrets are logged; no prototype-pollution, ReDoS or unbounded-loop patterns; the relayer proxy validates before key use and requires byte-equal auth roots. All 45 contract error codes, names and families match the Rust enums; OZ `main` (2026-09-04) adds no interface, error, event or limit changes over the pinned `1e513890`.
