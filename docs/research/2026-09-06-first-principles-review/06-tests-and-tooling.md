## Summary

The suite is fast, deterministic, network-free, and honest about where it is good: `relayer-proxy` (81 % lines, behaviour-driven through the Hono handler), `auth-payload.ts` (host-order `compareScVal` and the AuthPayload map are genuinely pinned), `wallet-provenance.ts`'s happy paths, `validation.ts`, storage adapters, and the drift tests that hold the hand-written error registry to the generated bindings. The biggest problem is that **the security-critical code added in v0.7.0 is largely asserted by coverage, not by tests**: the fresh-WebAuthn ownership gate, the "exactly one live signer" check, the birth-signer match, every rejecting branch of `verifyFreshAssertion`, every malformed-DER guard in `compactSignature`, and the delegated `__check_auth` nested entry can all be deleted and 414 tests stay green (§F2–F5, verified with branch coverage). Second, **nothing binds the SDK's output to what the contract verifies**: the only signing test asserts the WebAuthn challenge is 32 bytes and feeds an `authenticatorData` whose flags byte is `0x01` — a payload the deployed verifier rejects with `VerifiedBitNotSet` (§F3); the digest "golden vectors" were generated by the code under test. Third, the test-gap lens surfaced a real bug: `buildInvocationContextTypes` throws for *every* CreateContract auth entry, so `CreateContract` context rules are unreachable from the SDK (§F1). On tooling: test files are excluded from `tsc` and have never been type-checked (128 errors when included), `kit.ts` is tested by calling prototype methods on hand-built fake `this` objects so the 1707-line hub's wiring is 47 % covered and its constructor is invoked by one test, CI builds the SDK three times, runs the indexer-demo tests twice, and never runs lint/format/audit/bindings-drift/relayer-proxy typecheck (which fails). Packaging is ESM-only with `types` in the wrong position, sourcemaps that point at files not in the tarball, `@stellar/stellar-sdk` in both `dependencies` and `peerDependencies` with an unbounded `>=16.0.0`, and a jsr-only devDependency that makes `pnpm install` require jsr.io and drags in a `protobufjs` critical advisory. The rewrite should: put the auth core (digest, payload, DER, base64url, key-data, context-type extraction) in a dependency-free module with vectors generated from the Rust test suite and a WASM-in-the-loop conformance test; replace fake-`this` tests with tests that construct the real `SmartAccountKit` against a fake RPC; delete the separate bindings package, the version-sync script, both browser-audit scripts and the bespoke publish scripts in favour of one `pnpm check` and a provenance-enabled release workflow.

## Findings

### TEST-F1. `buildInvocationContextTypes` throws for every CreateContract auth entry — `CreateContract` context rules are unreachable, and no test notices   [severity: high]
- **Where:** `src/kit/context-rules.ts:102-112`, `src/kit/context-rules.ts:577-628`; consumer `src/kit/context-rules.ts:508` (`resolveContextRuleIdsForEntry`)
- **What:** `extractCreateContractWasmHash` duck-types the XDR union with accessor names `createContractHostFn`, `createContractWithCtorHostFn`, `createContractWithConstructorHostFn`. stellar-sdk 16's `SorobanAuthorizedFunction` has exactly two arms: `createContractHostFn()` and `createContractV2HostFn()`; the executable accessor is `wasmHash()`, not `wasm`. I built both arms and called the function: a `CreateContractV2HostFn` entry throws `createContractHostFn not set` (js-xdr union guard, unguarded by try/catch at line 588), and a legacy `CreateContractHostFn` entry throws `Unable to extract WASM hash …` because `execAny.wasm` is undefined. Every smart account deployed by this SDK uses a constructor, so any auth entry in which the wallet authorises a contract creation is a V2 entry, and context-rule resolution for it always throws. Coverage confirms lines 102–112 and 577–628 have zero hits; the only context-type test (`context-rules.test.ts:98-109`) uses `ContractFn`.
- **Why it matters:** correctness — the contract permits `ContextRuleType::CreateContract(wasm_hash)` rules (bindings line 253) and the SDK's builders let you create them (`builders.test.ts:57`), but the SDK cannot sign a transaction that would match one. It is exactly the kind of bug a contract-parity test would catch: the OZ `Context` enum has three variants and the SDK handles one.
- **Rewrite recommendation:** delete the duck-typing. `switch (fn.switch().name)` over the two real arms, read `fn.createContractV2HostFn().executable().wasmHash()` / `fn.createContractHostFn().executable().wasmHash()`, and add one test per arm that builds the real XDR (as my probe did). Better: generate the `Context → ContextRuleType` mapping test from the bindings' `Context` type so a third variant fails to compile.

### TEST-F2. The v0.7.0 fail-closed connect gates are covered by *absence*: deleting them keeps all 414 tests green   [severity: high]
- **Where:** `src/kit/wallet-ops.ts:476-482` (birth verification failure), `:494-507` (birth signer ≠ credential), `:544-549` (`liveMatches.length !== 1`), `:551-576` (fresh WebAuthn ownership assertion); `src/kit/wallet-provenance.ts:385-449` (every rejecting branch of `verifyFreshAssertion`)
- **What:** Branch coverage for the rejecting side: `wallet-ops.ts:494` `[0,2]`, `:544` `[0,1]`, `:551` `[0,1]`, `:557` `[0,0]`, `:570` `[0,0]`; `wallet-provenance.ts:385/397/400/406/416/419/423/426/432/447` all `[0,n]`. The two `connectWithCredentials` happy-path tests (`wallet-ops.test.ts:809-874`, `876-934`) store a credential with `birthConstructorArgsHash`, which makes `locallyApproved` true and skips the assertion block entirely; both also mock `verifyBirth` and `readContextRule`. `verifyFreshAssertion` is unit-tested only for accept / wrong-key / no-origins (`wallet-provenance.test.ts:288-337`): the challenge check, `type === "webauthn.get"`, the rpId hash, the UP/UV flags, the credential-id check and the malformed-DER path are never driven to reject.
- **Why it matters:** security — these checks are the headline of v0.7.0 ("fail-closed connect"). Mutation reasoning (table below) shows five of the seven most important checks in this flow can be removed without a failing test; a refactor that accidentally drops `challenge !== expectedChallenge` would ship. The tests that do exist assert the *unhappy* fail-closed paths well, which is why the number looks fine; they never assert that the *happy* path only opens after the full gauntlet.
- **Rewrite recommendation:** test `connectWithCredentials` as a state machine with a table: `{stored, indexer, birthTx, liveRule, assertion} → outcome`, where `birthTx` is a real `CreateContractV2` envelope (the `buildCreation` helper in `wallet-provenance.test.ts:45-92` already exists) and `assertion` is a real WebCrypto signature (the `freshAssertion` helper at `:248-286` already exists). One parametrised test with ~12 rows replaces 20 ad-hoc tests and covers every rejecting branch; for each row assert both the thrown error class *and* that `setConnectedState`/`saveSession` were not called.

### TEST-F3. Nothing binds the SDK's signing output to what the deployed verifier accepts; the one signing test feeds a payload the contract would reject   [severity: high]
- **Where:** `src/kit/webauthn-ops.test.ts:86` (`expect(base64url.toBuffer(optionsJSON.challenge)).toHaveLength(32)`), `:91` (`authenticatorData: base64url.encode(Buffer.alloc(37, 1))`); `src/kit/webauthn-ops.ts:170-185`; `src/signers.test.ts:25-33`; OZ `packages/accounts/src/verifiers/webauthn.rs:343-347`, `:151-163`
- **What:** (a) The only `signAuthEntry` test asserts the WebAuthn challenge is 32 bytes long; it does not assert it equals `base64url(sha256(sha256(preimage) ‖ scvVec(ids).toXDR()))` for the entry, expiration and rule ids actually passed. Passing the wrong expiration or the wrong ids into `computeEntryAuthDigest` would not fail it. (b) The fake authenticator data is 37 bytes of `0x01`, i.e. flags byte `0x01` = User-Present only. The deployed verifier calls `validate_user_verified_bit_set` (`webauthn.rs:346`) and panics with `VerifiedBitNotSet` (3117) unless `0x04` is set. So the unit test "signs" a payload `__check_auth` rejects, and nothing in the repo would notice. (c) The SDK requests `userVerification: "preferred"` in all three assertion paths (`webauthn-ops.ts:181`, `wallet-ops.ts:267`, `kit.ts:1094`); a roaming authenticator without a PIN legitimately returns UV=0 under "preferred", and the failure is an opaque on-chain error after the user has already tapped. (d) The "golden digest vectors (regression guard for the Rust formula)" in `signers.test.ts:25-33` were produced by `buildAuthDigest` itself; they guard against drift, not against being wrong. (e) `context-rules.test.ts:372-414` is the only vector captured from a real deployment, and it covers decoding, not signing.
- **Why it matters:** the SDK exists because "simulation cannot handle nested custom auth"; its whole value is producing bytes `__check_auth` accepts. Today that property is verified only by a human running `scripts/browser-full-e2e-audit.sh` against testnet (F9). 414 green tests say nothing about it.
- **Rewrite recommendation:** three layers. (1) **Vectors from Rust:** add a `#[test]` in the OZ example crate (or a tiny sibling crate pinned to `1e513890`) that, for a fixed `signature_payload`, `context_rule_ids`, P-256 key and WebAuthn client/authenticator data, prints `auth_digest`, the expected `challenge` string, and a `WebAuthnSigData` XDR that `verify` accepts; check the JSON into `src/auth/__vectors__/` and test `computeEntryAuthDigest`, `buildWebAuthnSignatureBytes`, `writeAuthPayload` against them byte-for-byte. (2) **Verifier-shape assertions in TS:** a `assertVerifierAcceptable(sigData)` helper (UP ∧ UV set, BE/BS consistent, `client_data ≤ 1024`, challenge == base64url(digest), type == `webauthn.get`) used in both `signAuthEntry` (fail fast with a typed error instead of an opaque host panic) and every test fixture; request `userVerification: "required"` for signing, or make it configurable with a loud default. (3) **WASM-in-the-loop conformance:** one CI job that starts `stellar/quickstart` (or uses `stellar-cli`'s local network), deploys the pinned `multisig_account_example`, `webauthn_verifier`, `ed25519_verifier` WASM, creates an account with a WebCrypto-generated P-256 key (no browser needed — build `clientDataJSON`/`authenticatorData` exactly as the `freshAssertion` test helper does), and submits one `execute` and one direct token `transfer` signed by the SDK. That is the only test that proves "the digest the SDK signs is what the contract verifies".

### TEST-F4. `compactSignature` (DER → compact, low-S) has no direct test; every guard's reject side has zero hits; low-S coverage depends on WebCrypto randomness   [severity: medium]
- **Where:** `src/utils.ts:297-353`; branch coverage `utils.ts:300,301,303,304,308,310,311,317,321,322,336,339` all `[0,3]`, `:344` `[2,1]`
- **What:** The parser is reached only through `signAuthEntry` (fixed `s = 0x22…`, never high-S) and `verifyFreshAssertion` (signatures from `crypto.subtle.sign`, random `k`, so the `s > n/2` branch is taken with p≈0.5 per run — the coverage I measured happened to hit it twice). None of the malformed inputs (wrong tag, long-form length, `r`/`s` length 0 or > 33, trailing bytes, `r`/`s` outside `[1, n)`) is tested. `utils.test.ts` covers only `deriveContractAddress` and SPKI extraction.
- **Why it matters:** this is the parser that turns untrusted authenticator output into the 64 bytes the host's `secp256r1_verify` consumes; the host enforces low-S, so a normalisation bug means every second signature fails on-chain — a bug that would also only surface in ~50 % of test runs.
- **Rewrite recommendation:** a table test of ~10 DER inputs (the 5 canonical shapes: minimal `r`, leading-zero `r`, 33-byte `r`, high-S, `s = n/2`, plus each malformed case) with expected compact hex, and a `fast-check` property `∀ (r,s) ∈ [1,n)²: compact(der(r,s)) == (r, min(s, n−s))`. Consider replacing the hand-rolled parser with `@noble/curves`' `p256.Signature.fromDER(...).normalizeS()` — stellar-sdk 16 already depends on `@noble/hashes` and `@noble/ed25519`, so `@noble/curves` is a near-free dependency and is what the host effectively does.

### TEST-F5. The delegated `__check_auth` nested entry and the ed25519 multi-signer path are built but never asserted   [severity: medium]
- **Where:** `src/managers/multi-signer-manager.ts:386-397` (ed25519: zero hits), `:414-461` (delegated entry), `src/managers/multi-signer-manager.test.ts:504-585`
- **What:** The only test that exercises a delegated signer reads `auth[0]` (the wallet's own entry) and checks the AuthPayload contains the passkey signature and an empty entry for the wallet. It never inspects `auth[1]` — the nested `SorobanAuthorizationEntry` whose invocation is `__check_auth(authDigest)` on the wallet, whose nonce is random, whose expiration must equal the outer entry's, and whose signature envelope is `buildAddressSignatureScVal`. Passing `signaturePayload` instead of `authDigest` at line 425, or a different expiration at 435/451, survives. The ed25519 branch (`signEd25519Digest`) is dead in tests: `canSignEd25519` is mocked to `false` in `makeDeps` (`:66`).
- **Why it matters:** the digest in the nested entry is what binds the delegated G-signer to the selected rule ids; it is the "rule-selection downgrade" defence for delegated signers.
- **Rewrite recommendation:** assert on `auth[1]` explicitly: decode the invocation, check `functionName === "__check_auth"`, `args[0] === authDigest` recomputed via `computeEntryAuthDigest` from `auth[0]`, `signatureExpirationLedger` equal on both, and verify the `Keypair` signature over `hash(HashIdPreimage)` with the real keypair instead of a mocked adapter returning `Buffer.alloc(64, 8)`. Add one ed25519 test that uses `Ed25519Signer` and verifies the bytes in the AuthPayload with `keypair.verify(authDigest, sig)`.

### TEST-F6. Test files are excluded from `tsc` and have never been type-checked: 128 errors when included   [severity: medium]
- **Where:** `tsconfig.json:22` (`"exclude": [..., "**/*.test.ts", "**/test-utils.ts"]`); `.github/workflows/ci.yml` (no test typecheck step); examples `src/kit.test.ts:18` (`toScAddress?.() ?? …` hack around a non-existent method), `src/kit/deploy-ops.test.ts:551`, `src/kit/auth-payload.test.ts:64`, `src/managers/multi-signer-manager.test.ts:577-580`
- **What:** Running `tsc --noEmit` over `src/**` with tests included yields 128 errors: 80× TS2835 (tests import `./kit` without the `.js` extension the NodeNext config requires — vitest tolerates it), 17× TS2339 (`base64url.encode` on the raw CJS default import that `src/base64url.ts` exists to fix — tests import `base64url` directly; `Property 'toScAddress' does not exist on type 'PublicKey'`), 14× implicit `any`, plus `Argument of type 'Buffer' is not assignable to parameter of type 'Hash'`. Vitest transpiles with esbuild, so none of this is ever seen. 130 `as never`/`as unknown as` casts hide the rest. (Caveat: 3 of the 128 are the uninstalled jsr dependency in `src/wallet-adapter.ts` and appear without tests too; test-file-only errors = 125.)
- **Why it matters:** maintainability — tests written against the wrong types drift silently; the `toScAddress?.()` hack is a test author guessing an API at runtime. A public-API change that breaks the tests' *types* but not their runtime is invisible until a consumer hits it.
- **Rewrite recommendation:** one `tsconfig.json` with `include: ["src"]` and no test exclusion, `noEmit` for `pnpm check`, and a separate `tsconfig.build.json` that excludes tests for emit. Delete the extensionless imports. Make `pnpm check` run `tsc -p tsconfig.json --noEmit` before vitest.

### TEST-F7. `SmartAccountKit` is tested by calling prototype methods on hand-built fake `this` objects; its constructor and wiring are effectively untested   [severity: medium]
- **Where:** `src/kit.test.ts:75-92` and 14 further `SmartAccountKit.prototype.<m>.call({...} as unknown as SmartAccountKit, …)` sites; `src/execute.test.ts:14-19`; `src/kit.ts:540-616` (manager wiring), `:1053-1110` (`connectWithCredentials` deps object), `:1631-1650`; only real construction: `src/indexer.test.ts:138`
- **What:** `kit.ts` is a 1707-line hub whose job is to assemble ~15 `deps` objects for the functions in `src/kit/*` and the managers. Those objects are where argument-order and field-name mistakes live (e.g. passing `acceptedWasmHashes` where `acceptedBirthWasmHashes` belongs). The tests bypass the constructor and every private method, supplying `vi.fn()` for each collaborator; they therefore test that a public method forwards to a private method with the expected name — i.e. they re-state the implementation. Coverage: 47 % statements, 74/111 functions never executed, including `createPasskey`, `connectWithCredentials`, `signAuthEntry`, `fundWallet`, `upgrade`, `policyClients`, `buildDeployTransaction`, `resolveConnectedContextRuleIds`, `sendAndPoll`. A `deps` typo is caught only by `tsc` (when the types happen to differ) or by the manual browser E2E.

## First-principles recommendations for the rewrite

1. **Carve out a pure `auth-core` module with zero I/O and zero mocks.** `src/auth/{digest,payload,der,base64url,keydata,context}.ts` exporting: `authDigest(preimageHash: Uint8Array, ruleIds: readonly number[]): Uint8Array`, `encodeAuthPayload(p: AuthPayload): xdr.ScVal` / `decodeAuthPayload`, `compareScVal`, `derToCompactLowS(der: Uint8Array): Uint8Array`, `webauthnSigData(...)`, `contextTypesOf(entry): ContextRuleType[]` (fixing F1). Test it three ways: (a) **vectors generated from the Rust test suite** (F3) checked in as JSON — digest, challenge string, `WebAuthnSigData` XDR, AuthPayload XDR with two same-verifier signers in host order, `Signer` XDR for all three variants, contract-id derivation; (b) **property tests** with `fast-check`: `decode(encode(p)) == p`, `compareScVal` is a total order consistent with `ScVal` XDR round trip, `derToCompactLowS(der(r,s)) == (r, min(s,n−s))`, `base64url` round trip on arbitrary bytes, `keyData(pk, cred)` splits back; (c) **cross-check against stellar-sdk** where it has a reference (`buildAuthorizationEntryPreimage`, `Address` XDR).

2. **One contract-level conformance test that runs the real WASM.** A `test/conformance/` vitest project that talks to `stellar/quickstart` (docker) or `stellar-cli`'s local network: upload the three pinned WASMs, deploy an account with a WebCrypto P-256 key, and prove `execute` + direct token `transfer` + an `add_signer` with a delegated co-signer + one `CreateContract` rule succeed **through the SDK's public API only**. Assert against the ledger (`getTransaction` SUCCESS + events), not against mocks. This single job is worth more than the current 400 unit tests for the question the brief asks. Run it on every PR (≈60–90 s with a cached image); the WASM hashes are already pinned in `docs/deployments-protocol-27-2026-07-09.md`.
