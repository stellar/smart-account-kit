## Summary

The satellites are where the SDK's "world-class" ambition is weakest. The relayer proxy is a carefully fail-closed validator (validation before key access, byte-equal auth roots, WASM allowlists, fee ceiling) — but as committed it cannot be called from a browser at all: its hand-rolled CORS preflight allows only `Content-Type` while the SDK unconditionally sends `X-Client-Name`/`X-Client-Version` (F1). It also imports `@stellar/stellar-sdk` without declaring it and only resolves the right (P27-aware) version by accident of the monorepo layout (F2). The SDK↔proxy contract is two hand-maintained shapes with heuristic parsing on the SDK side and no test that crosses the boundary (F9, F10).

The indexer is not "close to required"; it is required: without a complete schema-2 response a fresh device cannot connect even when it knows the contract ID, `rules.list()` silently under-reports, and the freshness gate demands the provider self-report a ledger at or past the one the SDK observed *before* the request — a check an honest, one-ledger-behind indexer fails and a dishonest one trivially passes (F11, F12). Meanwhile the SDK re-verifies almost every schema-2 field itself, so the minimal surface it truly needs is `credentialId → [{contractId, creationTxHash}]` (F13). Crucially, `rules.list()` needs no indexer at all: the OZ contract keeps `NextId` in instance storage and each rule under `ContextRuleData(id)` in persistent storage, so three `getLedgerEntries` calls enumerate the exact active rule set (F14) — this also exposes that `get_context_rules_count` is the *active* count, not the monotonic counter the SDK and README claim.

The bindings package leaks a generated `Client`, `Buffer`-typed contract structs, a global `window.Buffer` mutation and a wholesale `export * from "@stellar/stellar-sdk"` into the public API, and its "byte-compatible with the deployed WASM" contract is contradicted by the SDK's own shim for wallets whose `get_context_rule` lacks `signer_ids` (F17). The demo is a 5k-line admin console that re-implements SDK logic — including a policy-map sort by `localeCompare` that provably differs from Soroban host order because `rules.add()` does not sort (F19). Deployed addresses live in six hand-copied places and nowhere in the SDK (F21).

The rewrite should: publish a typed relayer protocol as a subpath export the worker imports; make the SDK's sponsor a pluggable interface with an HTTP default; make the indexer optional by reading rule state from ledger entries and treating discovery as a plug-in with a one-page spec; vendor the contract spec into `src/generated/` and delete the second npm package; replace the demo with `examples/` plus a separate console app; ship per-network typed manifests.

## Findings

### SVC-F1. Proxy CORS preflight rejects the SDK's own request headers   [severity: high]
- **Where:** `relayer-proxy/src/index.ts:105-110` (`setCorsHeaders` → `Access-Control-Allow-Headers: Content-Type`), `relayer-proxy/src/index.ts:91-95` (OPTIONS handling); `src/relayer.ts:218-222` (`X-Client-Name`, `X-Client-Version` sent on every request).
- **What:** Custom request headers force a preflight; the worker answers `204` with `Access-Control-Allow-Headers: Content-Type` only (verified by executing the worker with `Access-Control-Request-Headers: content-type,x-client-name,x-client-version`). Browsers then refuse the POST ("Request header field x-client-name is not allowed"). Before `f190326` (2026-08-03) the proxy used `hono/cors()`, which reflects requested headers; that commit replaced it with the hand-rolled version and no test covers allow-headers. `index.test.ts:470-490` only checks `Allow-Origin`.
- **Why it matters:** Every browser relayer submission from an allowed origin fails at preflight with the code as written. The demo (`demo/.env.example` → `VITE_RELAYER_URL`) is the only consumer and it *is* a browser. Either the deployed worker predates this commit or the browser path has not been exercised since. There is no SDK↔proxy integration test to catch it (see F10).
- **Rewrite recommendation:** One shared protocol module defines the header set and the CORS policy (F10). In the worker, use `cors({ origin: allowlist, allowHeaders: PROTOCOL_HEADERS })` or drop the custom headers entirely (they are not consumed anywhere on the proxy). Add a contract test: SDK client → in-process worker `fetch`, including preflight.

### SVC-F2. Proxy imports an undeclared `@stellar/stellar-sdk` and only gets a P27-capable version by accident   [severity: high]
- **Where:** `relayer-proxy/src/index.ts:9-21` (direct import), `relayer-proxy/package.json` (dependencies: only `@openzeppelin/relayer-plugin-channels`, `hono`), `relayer-proxy/pnpm-lock.yaml:451,1021` (`@stellar/stellar-sdk@14.6.1` transitively via the plugin), `.github/workflows/ci.yml:32-36` (`pnpm install --frozen-lockfile --ignore-workspace` with a comment that the proxy "is NOT a workspace member" — `pnpm-workspace.yaml` lists it).
- **What:** `relayer-proxy/node_modules` has no `@stellar`; the import resolves by directory walk to the repo root's `node_modules/@stellar/stellar-sdk` (16.0.1, verified). A standalone `cd relayer-proxy && pnpm install` (exactly what `relayer-proxy/README.md:55-58` instructs) yields only the plugin's 14.6.1 copy, which predates the `sorobanCredentialsAddressV2` union arm the proxy checks at `index.ts:551,590` — decoding a P27 wallet auth entry would throw or every wallet call would be rejected. When bundled by `wrangler deploy`, the worker can end up with two stellar-sdk copies (root 16.x for the proxy, 14.x inside the plugin). Two lockfiles (`pnpm-lock.yaml`, `relayer-proxy/pnpm-lock.yaml`) for one workspace member.
- **Why it matters:** Correctness for any self-hoster following the README; a silent version split inside the deployed bundle; and it undermines the "fail-closed" claim because the validation code's XDR vocabulary depends on which copy wins.
- **Rewrite recommendation:** Declare `@stellar/stellar-sdk` (pinned to the SDK's version) in the worker's `package.json`; delete the standalone lockfile and the `--ignore-workspace` install; make the worker depend on `smart-account-kit` (subpath exports, F10) so there is exactly one XDR vocabulary. Prefer a plugin version that peer-depends on stellar-sdk ≥16, or bypass the plugin: `ChannelsClient` is two HTTP calls.

### SVC-F3. The threat model is "rate-limited open faucet", and the limiter can be exhausted by invalid requests   [severity: medium]
- **Where:** `relayer-proxy/src/index.ts:86-90` (origin check only when an `Origin` header is present), `:794-807` (rate limit consumed *before* body parsing/validation), `:330-364` (global 100/min + per-IP 10/min, `constants.ts:56-58`), `:255-272` (one Relayer API key minted per client IP from a public `/gen` endpoint), `:150-154` + `wrangler.toml:46-48` + `package.json:8` (mainnet accepted in code, "testnet-only by policy" in config, `deploy:production` script still present).
- **What:** (a) `ALLOWED_ORIGINS` is not access control: any non-browser client omits `Origin` and passes. The real controls are the fee ceiling (`MAX_RESOURCE_FEE_STROOPS`, 0.1 XLM) and the two fixed-window counters. (b) Both counters increment before validation, so 10 IPs sending 10 garbage POSTs each per minute exhaust the global 100/min for everyone — a one-line DoS. (c) Per-IP API keys work *for* an attacker: each new IP mints a fresh Relayer key with a fresh 24h upstream quota (`README.md:20-21`). (d) An attacker who deploys their own allowlisted-WASM wallet (free, via this proxy) can then have the relayer pay for `execute(anyContract, anyFn, anyArgs)` (`DEFAULT_WALLET_FUNCTIONS` includes `execute`) up to the fee ceiling per call — so "can a client submit arbitrary func at the relayer's expense" is *yes, mediated by a wallet they control*. (e) Mainnet cannot actually run: there is no static `RELAYER_API_KEY` secret path; `getOrCreateApiKey` only knows `/gen`. The `README.md:3` claim "without exposing a Relayer API key" is misleading on testnet, where the key is mintable by anyone.
- **Why it matters:** Bounded to testnet XLM today, so not a loss-of-funds issue; but the README presents the proxy as a reusable pattern ("Use a matching proxy for another network", `demo/README.md`), and the SDK README tells integrators to point `relayerUrl` at their own copy. The honest framing — "this sponsors any allowlisted wallet's calls, capped per call and per minute; it is a faucet with shape checks" — is missing.
- **Rewrite recommendation:** State the threat model in one paragraph at the top of the README. Count global rate only after validation succeeds; keep the per-IP pre-check. Use a sliding window or token bucket (the Durable Object already exists). Replace per-IP minted keys with one operator secret (`RELAYER_API_KEY`) plus per-wallet quotas keyed by contract ID (the thing the proxy actually sponsors), and delete the mainnet branches or make them real. Consider a per-wallet daily stroop budget stored in the DO — that is the control that maps to the actual cost driver.

### SVC-F4. Signed-XDR route caps `resourceFee` but not the envelope fee the fee-bump must cover   [severity: medium]
- **Where:** `relayer-proxy/src/index.ts:751-763` (reads `ext.sorobanData().resourceFee()` only); `transaction.fee` is never inspected.
- **What:** A fee-bump's outer fee must be ≥ the inner transaction's fee rate × (ops+1). The client controls the inner `fee` field; the proxy validates only the Soroban resource fee component. Whether this drains anything depends on the OZ Channels service applying its own cap (`RelayerErrorCodes.FEE_LIMIT_EXCEEDED` suggests it does), which the proxy does not verify.
- **Why it matters:** Defense-in-depth gap in the one route where the client, not the relayer, builds the envelope.
- **Rewrite recommendation:** Cap `transaction.fee` (total) as well as `resourceFee`; or drop the XDR route entirely — dedicated-deployer users have a funded key and can submit directly, which the SDK already supports (`deploy-ops.ts:341-374` falls back to RPC).

### SVC-F5. Testnet retry loop has no backoff and the upstream coupling is string-matching   [severity: medium]
- **Where:** `relayer-proxy/src/index.ts:823-858` (`while (true)` retry), `constants.ts:43` (`MISSING_ACCOUNT_PATTERN` regex over error text), `constants.ts:27` (`API_KEY_FIELD_NAMES = ["apiKey","api_key","key","token"]` — guessing `/gen`'s response shape), `index.ts:200-233` (three legacy KV value formats with in-place migration), `wrangler.toml:23-30` (`cpu_ms = 300_000`).
- **What:** If `fundWithFriendbot` fails, or the relayer keeps reporting an already-funded account, the loop re-submits immediately with no sleep until the 5-minute deadline, holding a worker for up to 300 s of CPU. The missing-account detection depends on the exact phrase `Account not found: G...` in an upstream error message. The KV migration code exists to support key formats the proxy itself wrote in earlier versions.
- **Why it matters:** Robustness and cost (worker CPU is billed); the string matching is a silent-failure mode after any upstream wording change; the migration code is dead weight for a rewrite.
- **Rewrite recommendation:** Exponential backoff with a bounded attempt count; treat friendbot as an operator cron, not a request-path side effect (post-reset channel funding is an ops task); delete KV format migration; if `/gen` stays, pin its response schema in the protocol module.

### SVC-F6. The deploy constructor-shape check hard-codes today's one-passkey wallet and stops nothing   [severity: medium]
- **Where:** `relayer-proxy/src/index.ts:496-532` (`validateDeployConstructor`), compare `src/kit/wallet-provenance.ts:118-182` (`validateConstructor`) and `src/kit/deploy-ops.ts:432-447` (`buildDeployTransaction`).
- **What:** The check matches the SDK's current constructor exactly (two args, one `External` signer, key data `0x04||64 bytes||credentialId`, `salt == sha256(credentialId)`), so it is sound *for that shape*. It does not check the verifier address (`signer[1]` may be any address, `:518`), so an attacker-controlled verifier passes. It is trivially satisfiable with random bytes, so as "deploy-spam defense" it filters nothing an attacker would send. And it rejects every other legitimate birth the contract permits: Ed25519 initial signer (backend agent), Delegated G-address, multiple initial signers, policy-only wallets.
- **Why it matters:** It is the proxy encoding product policy ("wallets are born with exactly one passkey") that directly conflicts with the rewrite goal of full contract parity. It also duplicates `wallet-provenance.validateConstructor` with slightly different rules (that one checks the verifier; this one does not).
- **Rewrite recommendation:** Delete the shape check. What the sponsor needs is: allowlisted WASM hash, allowlisted deployer for `{func,auth}`, one auth entry byte-equal to the function, fee under cap, per-wallet/IP quota. If a shape rule is wanted, express it once in the SDK as `describeBirth(create): BirthDescriptor` and let the operator pass a predicate.

### SVC-F7. No idempotency and no way to recover a hash after a timeout; the SDK then strands the user's wallet   [severity: medium]
- **Where:** `src/relayer.ts:250-257` (timeout → `{success:false, errorCode:"TIMEOUT"}` with no hash), `src/constants.ts:146` (default timeout 360 000 ms), `src/kit/deploy-ops.ts:324-337` (no hash → `deploymentStatus: "failed"`), `src/managers/credential-manager.ts:229-251` (`sync`: address occupied + no local birth → `"occupied"`, "wallet birth is unverified"), `src/kit/wallet-ops.ts:394-412` (connect with no stored birth requires the indexer).
- **What:** For `{func,auth}` the relayer builds the envelope, so the client cannot precompute the transaction hash. If the client aborts (6 min) while the proxy's retry loop (up to 5 min, F5) or upstream eventually lands the tx, the SDK records `failed`, the next `sync` flips it to `occupied`, and the user's *own* freshly created wallet can only be connected if a schema-2 indexer supplies the birth claim. On-chain idempotency is fine (auth nonces), but the protocol offers no `GET /submissions/:key`.
- **Why it matters:** A plausible testnet-reset / slow-friendbot path to a locked-out primary wallet, purely from protocol design.
- **Rewrite recommendation:** Client-supplied `idempotencyKey` (sha256 of `func||auth` is natural) stored in the DO with the resulting hash; `GET /relay/:key` to recover. Independently, the SDK can recover its own birth without any indexer for recent wallets: `getEvents({ contractIds:[derived], startLedger: ledgerAtSubmit-1, filters:[topic "context_rule_added"] })` returns the creation tx hash (RPC event retention is days, not seconds).

### SVC-F8. Structure and hygiene: 915-line single file, Hono barely used, 10.8k-line generated types checked in, stale docs, duplicated SDK constants   [severity: low]
- **Where:** `relayer-proxy/src/index.ts` (whole), `relayer-proxy/worker-configuration.d.ts` (10 836 lines; project-specific content is `Env` at lines 9–24), `relayer-proxy/README.md:65` ("token IDs" — no such env var exists), `relayer-proxy/src/index.ts:77-82` (re-derives the shared deployer from the literal seed; `src/constants.ts:91`, `src/utils.ts:28-30`), `constants.ts:60-61` (`SIMULATION_SOURCE` = same all-zero key as `src/kit/tx-ops.ts:216-219`), `constants.ts:17` (`FRIENDBOT_URL` = `src/constants.ts:137`), `constants.ts:63-75` (wallet function list = the contract ABI, hand-copied), `index.ts:859-893` (raw upstream `error.message` returned to clients; status casts `as 400 | 403 | ...`).
- **What:** Hono is used for one middleware and three routes; CORS is hand-rolled instead of `hono/cors` (which is what broke F1). The generated Cloudflare types file is 410 KB and pollutes every grep; the `Env` union types for `RELAYER_BASE_URL` are literal to *this* `wrangler.toml`, so a self-hoster with another relayer URL gets a type error until they regenerate. Error responses forward arbitrary upstream messages (mild info leak: internal URLs/hosts in fetch errors).
- **Why it matters:** Maintainability and self-hostability; the duplicated constants are the visible symptom of the missing protocol package (F10).
- **Rewrite recommendation:** `src/{env.ts, limits.ts, validate/{deploy,invoke,transfer}.ts, upstream.ts, index.ts}`; `@cloudflare/workers-types` + a 20-line `env.d.ts` instead of the generated file (or gitignore it and generate in `pretest`); import deployer/constants/validators from the SDK's protocol subpath; return only protocol error codes to clients and log details server-side.

### SVC-F9. SDK↔relayer: two hand-maintained shapes, heuristic parsing, dead error-code enum, no cross-boundary test   [severity: medium]
- **Where:** `src/relayer.ts:22-43` (`RelayerResponse`), `:59-70` (`RelayerErrorCodes` — OZ Channels codes the proxy never emits; not consumed anywhere in `src/` outside this file), `:121-123` (`looksLikeErrorCode` regex), `:146-165` ("Backward compatibility: some relayer proxies return tx fields directly"), `:336-366` (`extractErrorCode` probes `code`, `errorCode`, `data.code`, `data.errorCode`, `data.error`, `error`); `relayer-proxy/src/index.ts:832-839` (`{success, data:{transactionId, hash, status}}`), `:867-879` (`{success:false, error, data:{code, details}}`); `src/relayer.test.ts` and `relayer-proxy/src/index.test.ts` each mock the other side.
- **What:** There is no shared type, no version field, no test that runs the real client against the real worker. The client's parsing is written to tolerate unknown proxies; the proxy's response is written without reference to the client. Status strings (`result.status`) are passed through untyped from the plugin.
- **Why it matters:** F1 is the concrete cost. Also DX: an integrator writing their own sponsor endpoint has to reverse-engineer the accepted shapes from `extractErrorCode`.
- **Rewrite recommendation:** See "protocol package" below. One discriminated request type, one discriminated response type, one `RelayErrorCode` enum, exported from `smart-account-kit/relayer-protocol`, consumed by both sides, with `validateRelayRequest()` used by the worker and a contract test that imports the worker module and drives it with the SDK client.

### SVC-F10. The indexer is required, not optional — and mainnet fresh-device connect is currently impossible   [severity: high]
- **Where:** `src/kit/wallet-ops.ts:398-412` (no stored birth → must have `lookupWalletCandidates` and a `complete` schema-2 lookup, even when `contractId` was supplied by the caller), `src/kit/context-rules.ts:364-393` (without indexer: probe ids 0..8, stop after 3 consecutive misses; a wallet with rules `{0, 4, 5}` lists `{0}`), `src/constants.ts:65-68`, `indexer/README.md:42-44` ("Mercury mainnet still served the legacy response… The SDK rejects the legacy mainnet response"), `README.md:404`.
- **What:** The brief's "close to required" undersells it. Every fresh-device connection and every complete rule listing depends on a third-party hosted service returning a bespoke schema that, per the repo's own README, mainnet did not serve as of 2026-09-04. `rules.list()` under-reporting is security-relevant: an app rendering "who controls this wallet" from `rules.list()` can miss an attacker-added rule with id > 8 or after a gap.
- **Why it matters:** Availability of the core product path on mainnet; silent incompleteness of an authorization-critical read.
- **Rewrite recommendation:** F12 removes the dependency for rule listing entirely. For connect, see F11 and the topology section: make discovery a plug-in and make "connect to a known contract ID" work from RPC alone.

### SVC-F11. The freshness gate is self-reported and fails honest indexers   [severity: high]
- **Where:** `src/kit/wallet-ops.ts:405-419` (`ledgerAtLookupStart = getLatestLedger()` **before** the lookup; then `lookup.indexedThroughLedger < ledgerAtLookupStart` → throw "stale"), `src/indexer.ts:339-350` (`complete` also requires every `creationLedger <= indexedThroughLedger` and `collision === (candidates.length > 1)`), `indexer/README.md:103` ("Keep `indexed_through_ledger` current with the network ledger at request time").
- **What:** The SDK requires the provider to claim it has indexed through a ledger that is at least the one the SDK saw *before sending the request*. Any provider that reports its actual indexed height and lags by one 5-second ledger fails every connection. The README resolves this by instructing providers to report the network's current ledger — i.e. not the indexed height — which makes the check pass by construction and verify nothing. `derived_address`, `collision`, `current_wasm_hash`, `incomplete` are all likewise provider claims that the SDK either recomputes (`wallet-ops.ts:420-433` recomputes collision; `verifyWalletBirth` recomputes wasm/deployer/salt) or cannot verify.
- **Why it matters:** Correctness against any non-Mercury provider; false sense of freshness; the only freshness-sensitive fact (a *later* second wallet for the same credential) is a UX ambiguity, not a security boundary, because birth verification is per-candidate.
- **Rewrite recommendation:** Delete `indexed_through_ledger`, `complete`, `incomplete`, `derived_address`, `collision`, `current_wasm_hash` from the required schema. Treat the indexer strictly as a hint source; verify each candidate against RPC; surface "N candidates" to the caller.

### SVC-F12. `rules.list()` needs zero indexer: read the contract's storage entries directly   [severity: medium]
- **Where:** OZ pinned `packages/accounts/src/smart_account/storage.rs:27-54` (`SmartAccountStorageKey::{ContextRuleData(u32), NextId, Count, SignerData(u32), PolicyData(u32)}`), `:56-70` (`ContextRuleEntry {name, context_type, valid_until, signer_ids, policy_ids}`), `:189-205` (`get_context_rule` = one persistent read + signer/policy reads), `:642,700,704` (`NextId` and `Count` in **instance** storage), `:876-884` (`Count` decremented on remove); SDK `src/kit/context-rules.ts:181-224` (one `simulateTransaction` per rule), `src/kit/wallet-ops.ts:372-377` (the instance entry is already fetched at connect).
- **What:** The instance ledger entry the SDK already fetches contains `NextId` and `Count`. `getLedgerEntries` accepts up to 200 keys per call. Algorithm: (1) read instance → `nextId`, `count`, wasm hash; (2) `getLedgerEntries(ContextRuleData(0..nextId))` → the exact live rule set (removed rules have no entry; if fewer than `count` come back, some are TTL-archived — a condition the current design cannot even detect); (3) `getLedgerEntries(SignerData(ids) ∪ PolicyData(ids))` → signers and policy addresses. Three RPC round-trips, no simulation, no indexer, no probe heuristics, no `hydrateContextRuleIds` shim (`context-rules.ts:130-179`), and `signer_ids`/`policy_ids` come for free. The entry types are `#[contracttype]` structs (symbol-keyed `ScMap`), ~40 lines to decode; gate the decoder on the accepted WASM hash list the SDK already maintains.
- **Why it matters:** Removes the single biggest external dependency for the most security-relevant read, and makes it exact. Side finding: `get_context_rules_count` returns `Count` (active rules incl. expired, decremented on removal), but `README.md:370`, `src/managers/context-rule-manager.ts:104-107` and `demo/src/components/ContextRulesPanel.tsx:82-83` document it as "total rules ever created, a monotonic counter". That is wrong; the monotonic value is `NextId`, which has no getter but is readable from instance storage.
- **Rewrite recommendation:** `rules.list()` ← storage read (default) with `simulate get_context_rule` as the fallback for unknown WASM. Delete `contextRuleProbe`, `getContractDetailsFromIndexer`, `DEFAULT_MAX_PROBED_RULE_ID`. Fix the `count()` docs or expose `{ active: Count, nextId }`.

### SVC-F13. Schema-2 is over-specified; address lookup is under-specified   [severity: medium]
- **Where:** `src/indexer.ts:24-55` (`IndexedContractSummary`, 14 fields), `:278-316` (strict credential validation), `:378-386` (`lookupByAddress` — no validation at all), `indexer/README.md:62-108`; consumers: `src/kit/wallet-provenance.ts:185-339` uses only `contractId`, `creationTransactionHash` (and `creationLedger` for a cross-check at `:248-253` that adds nothing once the envelope hash matches).
- **What:** The SDK verifies the creation transaction by hash and recomputes the derived address, WASM, deployer, salt and constructor from the envelope. ### SVC-F17. Demo re-implements SDK logic, and one re-implementation is wrong: policy-map sorting   [severity: high]

- **Why it matters:** A correctness bug at the SDK API boundary (any caller, not just the demo, will get this wrong), plus a catalogue of API debt: every one of these helpers is something the SDK should own.

## First-principles recommendations for the rewrite

### Service topology

| Layer | Required? | Shape |
|---|---|---|
| Stellar RPC | required | the only hard dependency; everything security-relevant is verified here |
| Horizon | optional | only for `getTransaction` beyond RPC retention when birth verification is requested |
| Sponsor (fee payer) | optional, pluggable | `interface Sponsor { submit(req: SponsorRequest): Promise<SponsorResult> }`; default `HttpSponsor(url)` speaks the protocol below; `KeypairSponsor(secret)` for Node backends (wraps what `tx-ops.sendAndPoll` does today on the RPC path) |
| Discovery (reverse index) | optional, pluggable | `interface Discovery { byCredential(idHex): Promise<Array<{contractId, creationTxHash?}>>; bySigner?(address): ... }`; implementations: `MercuryDiscovery`, `LocalDiscovery` (the SDK's own storage), `EventsDiscovery` (RPC `getEvents`, recent wallets only), `HttpDiscovery(url)` for the reference indexer |

Rules for the core: `connect({contractId, credentialId})` and `rules.list()` must work with RPC alone (F12). Birth verification becomes `connect({..., verifyBirth: { creationTxHash } | "discover" | false })` — required data comes from local storage, the caller, or a Discovery plug-in, never from a hard-coded vendor. Default for a derived-address primary wallet whose live state shows exactly the connecting passkey and the expected policies: connect without birth (live code + full live rule enumeration determines all future authorization; birth only adds "was constructed by the SDK", which the derived address already commits to for deployer+salt). Offer `strict: true` to require the tx-hash proof. This is a product decision — see open questions.

### `smart-account-kit/relayer-protocol` (subpath export, zero heavy imports)

```ts
export const RELAY_PROTOCOL = 1 as const;
export const RELAY_HEADERS = ["content-type", "x-relay-client"] as const;

export type RelayRequest =
  | { v: 1; kind: "invoke";   func: string; auth: string[]; key: string }   // key = hex sha256(func||auth)
  | { v: 1; kind: "deploy";   func: string; auth: string[]; key: string }
  | { v: 1; kind: "envelope"; xdr: string; key: string };                   // dedicated deployer, optional route

export type RelayErrorCode =
  | "INVALID_REQUEST" | "NOT_ALLOWED" | "FEE_LIMIT" | "RATE_LIMITED"
  | "SIMULATION_FAILED" | "UPSTREAM_UNAVAILABLE" | "INTERNAL";

export type RelayResponse =
  | { ok: true;  hash: string; status: "PENDING" | "SUCCESS" | "FAILED"; ledger?: number }
  | { ok: false; code: RelayErrorCode; message: string; retryAfterSeconds?: number };

export function parseRelayRequest(body: unknown): RelayRequest;   // throws INVALID_REQUEST
export function isRelayResponse(value: unknown): value is RelayResponse;
// GET /relay/:key → RelayResponse (idempotent recovery, F7)
```

Also export the *validation helpers* the worker needs so the proxy is glue: `describeDeployment(func, auth)`, `describeInvocation(func, auth)` returning `{ wallet, fn, resourceFee?, birth? }` plus `assertAuthRootMatches(func, auth)`, `assertAddressCredentials(auth, "v2" | "v1")`. `wallet-provenance.ts` already contains half of this; the worker's copies (`validateDeployConstructor`, `validateAuthorizedInvocation`, `SHARED_DEPLOYER`) get deleted.

Target worker: ~250 lines — `env.ts` (parse once, typed), `limits.ts` (DO token bucket keyed by `ip` pre-validation and `wallet` post-validation), `validate.ts` (calls SDK helpers + operator predicates from env), `upstream.ts` (one `submit()` with backoff), `index.ts` (Hono routes + `cors()` from `hono/cors` using `RELAY_HEADERS`). One operator secret. No per-IP key minting. No mainnet/testnet branching except the friendbot cron.

### Indexer-optional design and a minimal self-hostable indexer

What the SDK actually needs from an index is one map: `credentialIdHex → contractId[]` (and `creationTxHash` if birth verification is wanted). The reference implementation is a single-topic event consumer:

- Subscribe to RPC `getEvents` with topic filters `["signer_registered", "*"]` and `["context_rule_added", "*"]` (no `contractIds` filter — network-wide). Both are in the contract spec (`packages/smart-account-kit-bindings/src/index.ts:642-652`). Persist `(contractId, credentialIdHex = keyData[65:] for External signers, firstSeenTxHash, firstSeenLedger)`; the first `context_rule_added` for a contract *is* the creation transaction because the constructor emits it.
- Two endpoints: `GET /v1/credential/:hex → [{contractId, creationTxHash}]`, `GET /v1/signer/:address → [{contractId}]`.
- ~200 lines of Node + SQLite; cursor-paginated `getEvents` with the cursor persisted; backfill beyond RPC retention from any ledger data lake (Galexie/`stellar-etl`) — documented as the one place a hosted provider (Mercury) adds value.
- The SDK verifies WASM and live signer state itself; the index stores claims only.

Retire schema-2. Keep `indexer/` as `services/discovery/` with `SPEC.md` + the reference implementation + the `MercuryDiscovery` adapter if Mercury serves the two routes.

### Bindings

`src/generated/smart-account.spec.ts` (base64 spec array + `SPEC_WASM_HASH`), `src/generated/policies/*.spec.ts` for the three example policies, and a test that recomputes the spec from checked-in `.wasm` files under `contracts/` (or from the pinned upstream commit in CI). Public types are hand-written in `src/types/contract.ts` with `Uint8Array`. No `smart-account-kit-bindings` package, no `scripts/bindings/`, no `verify:bindings`, no `window.Buffer`.

### `examples/`

Each is one file, ≤ 100 lines, runnable with `pnpm example <name>`, using `networks.testnet` and no environment variables:

1. `01-create-and-transfer.ts` — passkey → `createWallet` → friendbot → `transfer`. Browser.
2. `02-add-device.ts` — second passkey on rule 0 via `signers.add`, connect from the "new device" with `connect({contractId})`. Browser.

## Open questions for Tyler

1. **Birth verification vs. live-state verification.** v0.7.0 made connect depend on a verified creation transaction. Given that the derived address already commits to deployer+salt and full live rule enumeration (F12) reveals every current signer/policy, is the residual threat birth verification addresses ("a wallet at my derived address constructed by a malicious relayer whose extra control was later removed") worth requiring an indexer on every fresh device? Would `strict` (birth required) vs `default` (live-state) modes be acceptable?
2. **Is the deployed proxy running code from before `f190326`?** If the demo's fee-sponsored path works in production today, the deployed worker predates the CORS change; if it doesn't, F1 explains it. Either answer changes how urgent F1 is versus "fix in the rewrite".
3. **Mercury relationship.** Is Mercury willing to serve a two-route minimal schema, or is the schema-2 contract something they built to your spec and would prefer to keep? Does SDF want to run the reference discovery service?
4. **Does the relayer need to exist on mainnet at all?** The OZ Channels model with per-IP minted keys is testnet-only. On mainnet the "proxy" is necessarily the integrator's own backend with their own key. Should the repo ship a *reference sponsor endpoint* (example 06) rather than a Cloudflare-specific worker?
5. **Rule count semantics.** `get_context_rules_count` is the active count (F12). Was the "monotonic" wording intentional (maybe from an earlier OZ revision), and does the P27 revision in progress add an id iterator or a `next_id` getter that would make the storage read unnecessary?
6. **Constructor parity.** With the shape check removed (F6), do you want the SDK to support non-passkey births (Ed25519 first signer for backend wallets, multi-signer births) in `createWallet`, or keep passkey-first as a product stance while exposing `deploy({signers, policies})` as the general primitive?
7. **`examples/` runtime.** Is a local quickstart (`stellar container start`) acceptable for the integration test, or must everything target public testnet (and therefore tolerate resets)?
