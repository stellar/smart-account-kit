# smart-account-kit — first-principles review: executive summary

**Subject:** `stellar/smart-account-kit` at `main@1a0c0eb` (v0.7.0 unreleased), plus `relayer-proxy`, `indexer/`, `packages/smart-account-kit-bindings`, and `demo/`, reviewed against OpenZeppelin `stellar-contracts@1e513890` (the deployed Protocol 27 artifacts) and OZ `main@6ea3075` (2026-09-04).
**Date:** 2026-09-06.
**Method:** six parallel area reviews (security, API/DX, architecture, contract parity, tests/tooling, services) each reading the relevant source in full, cross-checking against the Rust contracts, the Soroban host source, and stellar-sdk 16.0.1 internals, and running probes where a claim could be executed rather than inferred. Baseline: `tsc` clean, 414/414 tests green. Every finding cites `file:line`; every area doc opens with an honest coverage statement. Nothing in the repo was modified.
**Brief:** no legacy or backwards-compatibility constraints; evaluate as if rewriting from first principles toward a world-class SDK — secure, readable, simple, low code / high value, exposing everything the contracts permit.

---

## 1. The one-paragraph verdict

The hard, security-critical core is right: the auth digest the SDK signs is byte-identical to what `__check_auth` computes, signers only ever sign that digest, the host-order `ScMap` sort is correct (verified against `rs-soroban-env`), DER parsing is bounds-checked, nothing secret is persisted or logged, all 45 contract error codes match, and the v0.7.0 connect path really is fail-closed against a hostile indexer. What is *not* right is everything around that core: the trust model is implicit (the RPC is inside the signing trust base — one biometric tap signs whatever `simulateTransaction` returns), the wallet address does not commit to the constructor (so ~400 lines of provenance code compensate for a property the salt could simply guarantee), the passkey-wallet product is baked into a client for a contract that is far more general (backend agents and multi-signer births are unreachable), the public surface is the accretion history of the demo (151 exports, 24 config options, seven "signer" concepts, four error models, five signing pipelines), hand-maintained mirrors of the contract have drifted (unsorted policy maps, wrong XDR accessor names, `count()` documented backwards), the satellites carry more complexity than the SDK needs from them (a required indexer that isn't required, a relayer proxy whose browser path is broken as committed, a bindings package that re-exports all of stellar-sdk), and the test suite — fast and honest as it is — covers the v0.7.0 security gates by absence and never binds SDK output to the contract. A from-scratch version with full parity is realistically 3,000–3,500 lines of code against 8,580 today.

## 3. The ten findings that matter most

Ranked by how much they change the rewrite, not by severity label. IDs point into the area docs; the full cluster map is in [10-findings-register.md](10-findings-register.md).

**1. The RPC can choose what the passkey signs (SEC-F1, high).** Every signing path takes `simulationData.result.auth` and signs each entry's root invocation without ever comparing it to the host function the SDK itself built. Soroban auth entries are portable, so a malicious or MITM'd RPC returns one entry whose root is `USDC.transfer(wallet → attacker, balance)`, the user sees a contentless Touch ID prompt, and the attacker submits the signed entry from any funded account. The deploy path already contains the exact check that is missing everywhere else (`deploy-ops.ts:483-508`). *Rewrite:* intent-bound signing — `sign(entry, intent)` refuses anything the intent doesn't explain; ~40 lines; removes the RPC from the signing trust base.

**2. The address doesn't commit to the birth (SEC-F2, high; SVC-F6, SVC-F10).** `contractId = f(deployer, sha256(credentialId))` with a public deployer seed means anyone who learns a credential ID first can deploy any WASM with any constructor at the victim's address — and the relayer-proxy operator sees every credential ID before submission. The SDK fails closed afterwards, but the address is burnt and the "occupied" state, `expectedDeployer/Salt/Policies`, the relayer's constructor-shape check, and the `defaultPolicies`↔connect coupling (SEC-F10) all exist to compensate. *Rewrite:* `salt = sha256(wasmHash ‖ xdr(constructorArgs))`; verification reduces to "recompute the address from the birth tx". This is the single largest design decision — see [09-decisions.md](09-decisions.md) D2.

**3. Three verified correctness bugs at the API boundary.** (a) `rules.add()` and the constructor path pass an **unsorted** policies `Map`; the host rejects it for ≥2 policies depending on address order, and the demo's `localeCompare` workaround is provably wrong (PAR-F1 / API-F4 / SVC-F17). (b) `CreateContract` context rules are unreachable: the XDR extractor probes accessor names that don't exist and throws on every `CreateContractV2` entry (SEC-F9 / ARCH-F13 / TEST-F1). (c) `execute()` and `policies.add()` require pre-encoded `xdr.ScVal`s while the README and the managers' own JSDoc pass raw values and throw (PAR-F2). All three were confirmed by executed probes.

**4. The indexer is required, and it doesn't need to be (SVC-F10/F11/F12, PAR-F8, high).** Fresh-device connect throws without a complete schema-2 response even when the caller supplies the contract ID; mainnet Mercury serves the legacy shape per the repo's own README; `rules.list()` silently stops at rule id 8; the freshness gate demands a self-reported ledger that an honest one-ledger-behind indexer fails and a dishonest one trivially passes. Meanwhile the contract keeps `NextId`/`Count` in instance storage and each rule in `ContextRuleData(id)` persistent storage, so **three `getLedgerEntries` calls enumerate the exact live rule set with no indexer, no probe, no simulation** — and expose that `get_context_rules_count` is the *active* count, not the "monotonic counter" the SDK documents. *Rewrite:* RPC-only `rules.list()`; the indexer becomes an optional `Discovery` plug-in for credential → contract reverse lookup only.

**5. Connection is passkey-only; the contract is not (API-F1, PAR-F4, SVC-F6, high).** `_contractId` can only be set by a WebAuthn ceremony; birth must be exactly one WebAuthn signer on the configured verifier; `Delegated` means G-address only; custom verifiers can be registered but never sign. A Node backend holding an Ed25519 key on rule 3 cannot sign or submit anything through the kit. The OZ README's headline use cases — backend automation, AI agents with constrained access — are exactly the callers this SDK cannot serve. *Rewrite:* a general `SmartAccount` (any birth, any signer mix, one `Signer` interface) with the fail-closed passkey wallet as a *profile* on top, in a `/passkey` subpath.

**6. `userVerification: "preferred"` against a verifier that requires UV (SEC-F4, PAR-F10, TEST-F3).** Every registration and assertion path asks for "preferred"; `webauthn.rs:346` unconditionally requires the UV flag. A security key without a PIN registers as a wallet's sole signer and can never sign — discovered after funding. The browser E2E scripts mask this by configuring the virtual authenticator with `isUserVerified: true`.

**7. The browser relayer path is broken as committed (SVC-F1, SVC-F2, high).** The hand-rolled CORS handler (introduced in `f190326`, replacing `hono/cors`) allows only `Content-Type`; the SDK unconditionally sends `X-Client-Name`/`X-Client-Version`, so every browser preflight fails. The worker also imports `@stellar/stellar-sdk` without declaring it; a standalone `pnpm install` per the README resolves 14.6.1, which predates the P27 credential arms the worker checks. Either the deployed worker predates that commit or the path hasn't been exercised since — an open question.

**8. Architecture: a ball of mud with dependency injection (ARCH-F1/F2/F14, high).** `kit.ts` exists to build 15 different "deps bags" of ~30 closures that reach back into its own private state (`requireWallet` ×35, `getContractId` ×19); the runtime call graph is cyclic; tests forge the kit as `{ _contractId } as unknown as SmartAccountKit`. Connection state has ≥7 sources of truth and two different functions named `setConnectedState`. Five hand-rolled "keypair signs an auth entry" blocks duplicate stellar-sdk 16's `authorizeEntry`. *Rewrite:* values not sessions, one pure `authorize()` pipeline, lean on stellar-sdk, three entry points (core / passkey / node).

**9. The security gates are tested by absence (TEST-F2/F3/F4/F5, high).** The fresh-WebAuthn ownership block, exact-live-signer check, birth-signer match, every rejecting branch of `verifyFreshAssertion`, every malformed-DER guard, and the delegated nested `__check_auth` entry can all be deleted with 414 tests green. The digest golden vectors were produced by the code under test. The only signing test feeds a UV=0 payload the contract would reject. The only real `__check_auth` exercise is an author-only shell script scraping the demo's log text against public testnet and SDF's hosted relayer. *Rewrite:* KAT vectors generated from the Rust test suite, real-kit tests against a fake RPC, and a WASM-in-the-loop conformance job on a local network in PR CI.

**10. Surface, config, vocabulary, docs (API-F5/F6/F7/F8/F9/F11).** Six ways to say "threshold policy, N=2", two of them documented wrong. "Wallet" means three things. 24 config options where `{ network: "testnet" }` would do. The README quick start cannot run. `README:404` says the opposite of `context-rules.ts:229`. Three documented events are never emitted. The migration guide references a method that doesn't exist. None of the three docs Tyler asked OZ for (runnable hello-world, lifecycle page, error reference) exists here either.

## 4. Cross-cutting themes

**Trust boundaries are implicit.** RPC, Horizon, indexer, relayer and simulation output each get a different, unstated level of trust. The indexer is treated as hostile (correctly, thoroughly); the RPC is treated as honest for both state and *what to sign*; the relayer's hash is taken at face value for everything but deploys. A rewrite should make these boundaries types (`TrustedRpc`, `UntrustedSimulationAuth`, `UntrustedIndexer`, `UntrustedRelayer`, `UntrustedHistory`) so every crossing is visible in a review and every verification is a pure function over already-fetched facts.

**The product is baked into the core.** Single-passkey birth, rule 0 as the primary rule, "prefer scoped over Default", `defaultPolicies` as the expected constructor, the relayer's constructor-shape check — all of these are passkey-wallet product decisions expressed as global assumptions in a client for a general contract. The contract's own abstractions (`Verifier`, `Policy`, `Delegated(Address)`, `CreateContract` context) are the extension story, and the SDK exposes only the registration half of each.

**Parity is hand-maintained.** Only the account binding is generated; the three policies and two verifiers have hand-written types and encoders; the error registry is a hand-copied table with a drift test; limits are constants with a comment; events are ignored. Each of these has drifted at least once (`signer_ids` shim, `count()` doc, unsorted maps). Parity should be a `pnpm gen` step over the six pinned WASMs, and a CI diff against OZ `main`.

**The API is the demo's history.** The demo is the only consumer, and the surface grew by exporting whatever it needed next: `signFeePayer`, `resimulateAndAssemble`, `PolicyClientDeps`, UI string formatters. The demo in turn re-implements SDK logic (a rule-edit planner, unit conversions, a wrong policy sort, re-verifying what `connectWallet` verified) because the API shape made the right thing hard. A rewrite should ship ~25 root exports and an `examples/` directory of ≤100-line files; the admin console becomes `apps/console/`.

**The satellites are heavier than the SDK's needs.** A 915-line worker with per-IP minted keys and a testnet friendbot retry loop, a schema-2 indexer contract whose fields the SDK mostly re-verifies or ignores, a separately published bindings package with a `window.Buffer` side effect, and a 5k-line demo. What the SDK actually needs from services is one map (credential → contract IDs), one sponsor endpoint (a typed `{func, auth}` protocol), and per-network manifests in source.

## 5. What is good and should be kept

Explicitly, so the rewrite doesn't throw it away: the digest/payload core in `auth-payload.ts` and `signers.ts` (byte-identical to the contract, well-tested, host-order sort verified); the DER→compact parser's guards; the deploy path's simulation-vs-operation check (generalize it, don't delete it); `verifyFreshAssertion`'s WebCrypto verification; the fail-closed *structure* of `connectWithCredentials` (turn it into a pipeline of pure checks); the relayer proxy's validate-before-key-use discipline and byte-equal auth-root check; the error registry's completeness (generate it instead); `compareScVal` (upstream it); the mainnet deployer hardening invariants and the read-only check script; the deployments manifest (move it into source); and the honest "unaudited" security posture in `SECURITY.md`.

## 6. The shape of the rewrite

One package, three entry points. `smart-account-kit` is an isomorphic core over `Uint8Array` with zero runtime dependencies besides a `^16` peer on `@stellar/stellar-sdk`: a tiny pure `auth/` module (digest, payload codec, host-order compare, DER, contexts-of-entry, intent matching, expiration policy, signer validation) tested against vectors generated from the Rust suite; one `Signer` interface with Ed25519 and Delegated implementations; an immutable `SmartAccount` value whose reads come from ledger entries and whose writes are thin builders over generated clients for all six WASMs; `PolicyInstall` values (`policy.threshold(2)`) with typed clients and a plugin interface mirroring the Rust `Policy` trait; one `authorize(tx, { signers, intent, ruleIds? })` pipeline and one `submit(tx, sponsor)` + `confirm(hash, intent)`; a `Sponsor` interface (HTTP relayer speaking a typed, versioned protocol exported from a `/relayer-protocol` subpath; keypair; custom) and a `Discovery` interface (events, HTTP, Mercury, local). `smart-account-kit/passkey` is the browser profile: `PasskeySigner.register/authenticate` over `navigator.credentials` directly, `discover()` and a fail-closed `connect()` built as a pipeline of pure checks over fetched facts, session storage. `smart-account-kit/node` re-exports keypair signers and sponsors. Config is `{ network: "testnet" | "mainnet" | NetworkConfig, sponsor?, discovery?, storage? }` with `networks.*` manifests generated from one JSON file. Errors are thrown, typed, with string-union codes; `send()` returns a `Receipt { hash, ledger, returnValue, events }`. The full design — public API, module layout with LOC budget, trust model, service topology, test strategy, build order — is in [08-rewrite-blueprint.md](08-rewrite-blueprint.md).

## 7. What needs your decision

Twenty decisions only the author/product owner can make are consolidated in [09-decisions.md](09-decisions.md), each with options and a recommendation. The five that gate everything else: whether the RPC is meant to be trusted for signing (recommendation: no); whether the address derivation may change to commit to the constructor (recommendation: yes, for 1.0); whether birth verification stays mandatory or becomes a `strict` mode over live-state verification; whether backend/agent (non-passkey) use is a v1 requirement (recommendation: yes — it is the contract's headline use case); and whether the bindings package, the schema-2 indexer contract, and the Cloudflare worker survive as published artifacts (recommendation: vendor, retire, and replace with a reference sponsor endpoint respectively).

## 8. Things worth fixing on `main` before any rewrite

Independent of the rewrite, these are small, verified, and cheap: use `cors()` from `hono/cors` with the SDK's header set (SVC-F1); declare `@stellar/stellar-sdk` in the worker and delete its lockfile (SVC-F2, TEST-F11); sort the policies map with `compareScVal` in `rules.add` and `buildConstructorPolicies` (PAR-F1); fix the `CreateContract` accessor names (ARCH-F13); request `userVerification: "required"` (SEC-F4); reject the shared deployer as a signer in `validateSigner` (SEC-F7); validate the attestation fallback key with a WebCrypto import (SEC-F5); clamp signature expiration and stop rewriting it on already-signed entries (SEC-F8); fix the `count()` docs (PAR-F8); fix the README/JSDoc examples for `execute`/`policies.add`/`rules.add` (PAR-F2, API-F11); and add the missing tests for each of the above so the next refactor can't silently undo them (TEST-F2).
