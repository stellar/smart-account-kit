## Patterns

Citations are overwhelmingly accurate: 20 of 22 rows are fully confirmed, and in every confirmed row the cited range starts and ends on the exact construct named (function signature to closing brace, or the exact statement), which suggests the reviewers cited from a live editor rather than from memory. The empirical claims that I re-ran — the SEC-F5 garbage-key probe, the 128-error tsc count with its 80/17/14 breakdown, the publint 2-error/1-warning result, and the 94/59/41 throw/return counts — all reproduced exactly.

The discrepancies cluster in two places. (1) **Grep-derived headline numbers are occasionally the wrong regex or off by a modest amount:** API-F8's "20 `console.warn|error` calls" is really 20 `console.*` mentions including JSDoc examples (5 real warn/error calls); API-F9's 135 exports is 151; TEST-F6's "111 casts" is 130. None of these changes a conclusion, but the console number is overstated 4× and should be corrected. (2) **The contract-parity doc's README line numbers drift** while every other doc's README citations are exact: PAR-F8/PAR-F13 cite README:369 for a line at 370 and README:397-399 for the note at 404-406, and `builders.ts:166-167` for text at 168-169 — the same note is cited correctly as 404-406 in API-F11 and as README:370 in SVC-F12. The PAR reviewer's README:261,265 (PAR-F2) are correct, so this is not a constant offset, just a few hand-copied numbers in one doc. There is no systematic off-by-N in the source-code citations across any doc; `storage.rs` line references into the pinned OpenZeppelin tree were exact in every case checked.

One environmental caveat worth adding to TEST-F6: 3 of the 128 errors are the uninstalled jsr dependency (`@creit-tech/stellar-wallets-kit`) in `src/wallet-adapter.ts`, present even with tests excluded, so a reader who installs from jsr will see 125.
