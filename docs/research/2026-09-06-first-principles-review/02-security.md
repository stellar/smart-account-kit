## Summary

The cryptographic core is in good shape: the auth digest is built exactly as `do_check_auth` computes it (`sha256(sha256(P27 preimage) ‖ ScVec<u32>.toXDR())`), signers only ever sign that digest, the WebAuthn challenge is `base64url(digest)` matching `validate_challenge`, DER→compact conversion is bounds-checked with low-S normalization and curve-order range checks, the AuthPayload/WebAuthnSigData maps are emitted in host key order with a careful comparator, nonces and challenges use `crypto.getRandomValues`, and nothing secret is ever logged or persisted. The v0.7.0 connect path is genuinely fail-closed against a malicious *indexer*: the derived address (or caller-supplied `contractId`) is authoritative, the birth envelope is bound to its hash, the created contract ID is recomputed from the CreateContractV2 preimage, and the constructor is validated before a fresh assertion is checked against the *on-chain* key.

The biggest problem is not a bug but an unstated trust boundary: **the Soroban RPC is fully inside the signing trust base and the SDK never checks that simulation-returned auth entries correspond to the host function the user intended** (F1). Because Soroban auth entries are portable, a malicious or MITM'd RPC can obtain a passkey signature over an arbitrary invocation (e.g. drain the wallet) simply by returning it from `simulateTransaction`; a passkey prompt shows nothing. The deploy path already contains the exact check that is missing everywhere else (`deploy-ops.ts:483-508`). The second structural issue is that the shared-deployer address does not commit to the constructor (F2); most of `wallet-provenance.ts` exists to compensate, and a salt that commits to `(wasm, constructorArgs)` would delete squatting, the "occupied" state, `expectedDeployer/expectedSalt/expectedPolicies`, and the fresh-device `defaultPolicies` coupling (F10) in one move.

Below that: the relayer's returned hash is trusted for non-deploy transactions (F3); the SDK asks for `userVerification: "preferred"` while the deployed verifier hard-requires UV=1 (F4); the attestation public-key fallback can produce a garbage key that gets deployed as a wallet's only signer (F5); the shared deployer can be added as a Delegated signer, handing the wallet to the world (F7); signature expiration is unbounded and silently rewritten on re-sign (F8); and `CreateContract` context rules are unreachable through auto-resolution because of wrong XDR accessor names (F9). The rewrite should: (1) extract a tiny, pure, KAT-tested `auth-core`; (2) make "intent" a first-class value and refuse to sign anything the intent does not explain; (3) type the trust boundaries (`TrustedRpc` vs `UntrustedIndexer`/`UntrustedRelayer`/`UntrustedHistory`) so a reviewer can see every crossing; (4) commit the address to the birth.

## Findings

### SEC-F1. Simulation-returned auth entries are signed blind — the RPC can choose what the passkey signs   [severity: high]
- **Where:** `src/kit/tx-ops.ts:552-561` (`signResimulateAndPrepare` signs every entry in `authEntries` as-is), `src/kit/tx-ops.ts:679-693` (`signAndSubmit` feeds `simData.result.auth` straight in), `src/kit/tx-ops.ts:612-626` (`sign` → stellar-sdk `signAuthEntries` over `this.built.operations[0].auth`), `src/managers/multi-signer-manager.ts:286-406` (same, plus delegated `__check_auth` entries for the same digest), `src/kit/webauthn-ops.ts:170-185` (digest → WebAuthn challenge with no intent check). Contrast with `src/kit/deploy-ops.ts:483-508`, which *does* verify the simulation's auth entry against the operation.
- **What:** Every signing path takes `simulationData.result.auth` (or the assembled tx's `auth`) — bytes produced by `rpc.simulateTransaction` — and computes the digest over `entry.rootInvocation()` without ever comparing that invocation tree to the host function the SDK itself built (`buildTokenTransferHostFunction`, `wallet.execute(...)`). `assembleTransaction` (stellar-sdk 16.0.1 `rpc/transaction.js:79-89`) preserves the *signed* entries on re-simulation, so the re-sim step does not help; it only fixes fees. Nothing in the pipeline asserts "the entry I am about to sign authorizes the call I asked for".
- **Why it matters:** Soroban address-credential auth entries are portable: the signature covers `(networkId, nonce, expiration, invocation[, address])`, not the transaction. Anyone holding a signed entry can submit it in their own transaction whose invocation tree matches. **Attack narrative:** user calls `kit.transfer(USDC, friend, 5)`. The configured RPC (compromised provider, hostile reverse proxy in front of it, a TLS-terminating middlebox, or a malicious `rpcUrl` injected by a supply-chain/XSS bug in the app) answers the build-time simulation with one auth entry whose root invocation is `USDC.transfer(wallet → attacker, balance)`. The SDK asks the passkey to sign `sha256(preimage(that entry) ‖ [0])`. The user sees a Touch ID prompt with no content and approves. The SDK then re-simulates (attacker returns anything), submits via relayer (fails or succeeds, irrelevant) — meanwhile the attacker already has a valid, portable, ~1h-valid (F8: up to months) authorization and submits it from any funded account. Funds gone, one biometric tap. The same shape works for `execute`, `add_signer` (add attacker key), `upgrade` (attacker WASM). For passkeys there is no wallet UI in the loop, so the SDK *is* the last line of defense.
- **Rewrite recommendation:** Make intent a value and make the signer refuse to sign what intent does not explain. Something like:
  ```ts
  type Intent =
    | { kind: "invoke"; fn: xdr.InvokeContractArgs; allowSubInvocations?: (sub: xdr.SorobanAuthorizedInvocation) => boolean }
    | { kind: "deploy"; create: xdr.CreateContractArgsV2 };
  function assertEntryMatchesIntent(entry: xdr.SorobanAuthorizationEntry, intent: Intent, wallet: string): void;
  ```
  For `transfer`: root must equal `fn` byte-for-byte and `subInvocations.length === 0`. For `execute(target, fnName, args)`: root must be `wallet.execute(target, fnName, args)`; sub-invocations are normally empty (invoker auth), so refuse any. For contract-management calls: root must equal the bindings-built `InvokeContractArgs`. Only sign entries whose credential address is the connected wallet; pass everything else through untouched (today `signResimulateAndPrepare` also passkey-signs entries for *other* addresses and throws on `sorobanCredentialsSourceAccount` entries — see F6). Expose a `sign(entry, intent)` primitive and keep an escape hatch `signUnchecked(entry)` that is loudly named. The generalization of `deploy-ops.ts:483-508` is ~40 lines and removes the RPC from the *signing* trust base (it stays in the *state-reading* trust base — F11).

### SEC-F2. The shared-deployer address does not commit to the constructor: address squatting, pre-deposit theft, and most of `wallet-provenance.ts` exists to paper over it   [severity: high]
- **Where:** `src/utils.ts:165-183` (`deriveContractAddress`: salt = `sha256(credentialId)`), `src/kit/deploy-ops.ts:447` (`salt = hash(credentialId)`), `src/constants.ts:91` (public seed), `relayer-proxy/src/index.ts:496-532` (`validateDeployConstructor` — explicitly "not an ownership proof or a trust boundary"), `src/kit/wallet-provenance.ts:118-182,296-309` and `src/kit/wallet-ops.ts:456-475` (the compensating checks), `src/kit/wallet-ops.ts:186-194` (`createWallet` returns `contractId` before any deployment).
- **What:** `contractId = sha256(networkId ‖ deployer ‖ sha256(credentialId))`. Neither the WASM hash nor the constructor args are in the preimage, and the deployer's secret is public by design. Therefore anyone who knows a credential ID before the legitimate deploy lands can deploy *any* WASM with *any* constructor at the victim's derived address. The relayer proxy's shape check only requires that key data end in the credential ID; an attacker supplies `attackerPubKey ‖ victimCredentialId` and passes `hash(credentialId) == salt` (`index.ts:527-531`) — and the attacker does not need the proxy at all, any funded account can pay. The SDK fails closed afterwards (constructor/signer mismatch → `WalletOwnershipError`), which is correct, but the address is burnt forever and the user's "address = f(passkey)" property is gone.
- **Why it matters:** (a) **Griefing with a guaranteed oracle:** the relayer-proxy operator sees `{func, auth}` — i.e. the credential ID and public key — before it submits, and can front-run every deploy it wants. So can anyone on the path to the proxy. (b) **Theft if funds arrive before deployment:** `createWallet` hands back `contractId` even with `autoSubmit: false` and while `submitResult` is a failure; an app that shows it as a deposit address (the docs say don't, the API makes it easy) lets a squatter deploy with their own signer and sweep the deposit. (c) **Escalation with two lying sources:** a squatter deploys `[victimSigner, attackerSigner]` at the derived address; the victim's own deploy lands afterwards and fails ("already exists"). Later, on a fresh device, once the RPC has aged the tx out (`NOT_FOUND` → Horizon fallback), a colluding indexer (supplying the *failed* tx's hash/ledger as the birth claim) plus a lying Horizon (`successful: true`) passes every check in `verifyWalletBirth` — the presented constructor has one signer (the victim's), deployer/salt/policies match, live rule 0 contains exactly one matching signer — and the victim connects, with a valid fresh assertion, to a co-controlled wallet. Two colluding infra parties is a high bar, but the reason it is even possible is that the address does not commit to the birth. (d) **Cost:** ~400 lines (`wallet-provenance.ts`, half of `wallet-ops.connectWithCredentials`, `deploymentStatus: "occupied"`, `expectedDeployer/expectedSalt/expectedPolicies`, the `defaultPolicies` coupling of F10) exist to defend a property the address derivation could simply guarantee.
- **Rewrite recommendation:** `salt = sha256(wasmHash ‖ xdr(constructorArgs))` (or `sha256(xdr(CreateContractArgsV2 minus preimage))`). Consequences: an attacker who wants the victim's address must deploy the victim's exact wallet (a gift); the "occupied but unverified" state cannot exist; `verifyWalletBirth` reduces to "recompute the address from the birth tx's create args and compare"; `expectedPolicies`/`expectedSalt`/`expectedDeployer` disappear; per-call `policies` no longer break fresh-device recovery (F10). Credential-ID→address discovery already goes through the indexer in v0.7.0 (`lookupWalletCandidates`), and on the local device the SDK always has the public key and policies, so nothing user-visible is lost; the only thing that changes is that "derive the address from a bare credential ID with no other information" stops being possible — which is the property that enables squatting. Keep the shared deployer (it is harmless once the address commits) and keep it sign-only. Additionally, stop returning `contractId` from `createWallet` until `submitResult.success` (return `predictedContractId` with a doc-comment that it is not a deposit address) — or better, don't expose it at all before deployment.

### SEC-F3. Relayer-returned transaction hash is trusted; non-deploy submissions never verify the confirmed envelope   [severity: medium]
- **Where:** `src/kit/tx-ops.ts:112-149` (`sendAndPoll`: `hash = relayerResult.hash`, `pollTransaction(hash)`, `SUCCESS` → `{success: true, hash}`), `src/relayer.ts:146-205` (any `2xx` body with a `hash`/`status` string counts as success). Contrast `src/kit/deploy-ops.ts:109-152` (`confirmSubmittedDeployment` parses the envelope and asserts it contains the exact `CreateContractV2`).
- **What:** For `transfer`/`execute`/management calls the SDK reports `success: true` whenever *some* transaction with the relayer-supplied hash succeeded. A malicious or buggy relayer can return the hash of an unrelated successful transaction (or a previous one from the same user), and the SDK — and the app — will treat the intended operation as done.
- **Why it matters:** Not a fund-loss vector (the relayer cannot alter what the signed entries authorize), but it is an integrity gap: any app logic keyed on `result.success` (order fulfilment, "signer added", UI state) can be spoofed by the relayer. The deploy path already shows the right pattern.
- **Rewrite recommendation:** One `confirm(hash, intent)` used by every submission path: fetch the envelope, check `parsed.hash() === hash`, unwrap fee-bump, find exactly one `invokeHostFunction` op whose `func` equals the submitted host function byte-for-byte, and (cheap) check the auth entries it carries are the ones we sent. Return `{hash, ledger, envelope}` so the app can display/verify too. Also drop the "backward compatibility" success heuristics in `relayer.ts:154-165`; the proxy is yours — require `{success: true, data: {hash}}`.

### SEC-F4. SDK requests `userVerification: "preferred"` but the deployed WebAuthn verifier hard-requires UV=1   [severity: medium]
- **Where:** `src/kit/webauthn-ops.ts:85` (registration default), `:108`, `:181` (signing), `src/kit/wallet-ops.ts:267`, `src/kit.ts:1094`; contract `verifiers/webauthn.rs:345-347` (`validate_user_verified_bit_set` is unconditional in `verify`).
- **What:** With "preferred", an authenticator that cannot or does not verify the user (security key without PIN, some Android/Windows configurations, cross-platform keys) returns UV=0. The SDK happily registers such a passkey as the wallet's *only* signer and later produces signatures that `__check_auth` rejects with `VerifiedBitNotSet` (3117). The local `verifyFreshAssertion` does not require UV either (`requireUserVerification` is never set in `wallet-ops.ts:563-569`), so the SDK's own model is weaker than the contract's.
- **Why it matters:** Correctness/DX rather than exploitability: a user can end up with a deployed wallet that can never sign, and the failure is discovered after funding. It also means the SDK's stated security level ("passkey signs") is silently one notch below what the chain enforces.
- **Rewrite recommendation:** `userVerification: "required"` on registration and on every signing/ownership assertion; `residentKey: "required"` if fresh-device recovery via discoverable credentials is a product goal (today `"preferred"` at `webauthn-ops.ts:84` means non-resident keys can never be recovered with `connectWallet({prompt: true})`). Mirror the contract's flag checks (UP, UV, BE/BS) in one pure `checkAuthenticatorFlags(flags)` used by both the fresh-assertion verifier and a pre-flight on signing so the user gets a clear error before a doomed submission.

### SEC-F5. Attestation public-key fallback performs no final validation; a garbage key can be deployed as a wallet's only signer   [severity: medium]
- **Where:** `src/utils.ts:234-282` (`extractPublicKeyFromAttestation` fallback: hard-coded offsets in `authenticatorData`, `indexOf(prefix)` in `attestationObject` with `-1` unchecked, and the assembled `[0x04, ...x, ...y]` is returned without re-checking length/curve membership).
- **What:** Verified empirically: `extractPublicKeyFromAttestation({attestationObject: base64url(40 bytes of 0x07)})` returns a **32-byte** Uint8Array starting with `0x04`, no error. `createWallet` then stores it, `buildKeyData` concatenates it with the credential ID, and if the total is ≥ 66 bytes (any credential ID ≥ 34 bytes) the contract's `canonicalize_key` accepts the first 65 bytes as "the key" and the deploy succeeds. The wallet's only signer is now a point that is not the passkey's key (and may not be on the curve at all). The primary path (`response.publicKey` via WebCrypto SPKI import) is safe; the fallbacks are what most non-mainstream authenticators would hit.
- **Why it matters:** A wallet whose sole signer cannot ever produce a valid signature is a permanent fund sink. Low probability (modern browsers supply `response.publicKey`), catastrophic outcome, trivial fix.
- **Rewrite recommendation:** Parse properly (a 60-line CBOR reader for the COSE key: kty=2, alg=-7, crv=1, x, y) or, simpler, keep the fallback but *always* finish with `await crypto.subtle.importKey("raw", key, {name:"ECDSA", namedCurve:"P-256"}, false, ["verify"])` and `key.length === 65 && key[0] === 0x04` — WebCrypto rejects off-curve points. Better still: before storing anything, verify the registration's own attestation signature (`authenticatorData ‖ sha256(clientDataJSON)`) against the extracted key when `fmt === "packed"`/self-attestation is available; at minimum, verify a *fresh assertion* with the extracted key before deploying (you already have `verifyFreshAssertion`). "Key we can verify a signature with" is the only acceptable definition of "extracted correctly".

### SEC-F6. `signResimulateAndPrepare` signs every address-credential entry regardless of address and throws on source-account entries   [severity: low]
- **Where:** `src/kit/tx-ops.ts:552-561`; `src/kit/webauthn-ops.ts:138` (`getAddressCredentials` throws for `sorobanCredentialsSourceAccount`), no address check anywhere in `signAuthEntry`.
- **What:** Unlike `sign()` (which routes through stellar-sdk's `signAuthEntries({address: contractId})` and filters by address, `assembled_transaction.js:634`) and the multi-signer path (which branches on `authAddress !== contractId`), `signAndSubmit` passkey-signs *every* entry the simulation returned. If the passkey is a signer on two wallets and a tx (or a malicious RPC, F1) includes an entry for the other wallet, it gets signed silently using the connected wallet's rule IDs and signer identity. Any tx that also needs source-account auth crashes with "Soroban credentials do not contain address credentials".
- **Why it matters:** Same class as F1; on its own only a correctness/consistency gap between the three signing paths.
- **Rewrite recommendation:** One signing loop, used by all three paths: skip non-address credentials; sign only `address === wallet`; hand foreign G-address entries to external signers; refuse anything else unless explicitly allowed by intent (F1).

### SEC-F7. Nothing prevents adding the shared deployer as a Delegated signer — which hands the wallet to everyone   [severity: medium]
- **Where:** `src/validation.ts:70-75` (`validateSigner` checks only key size), `src/managers/signer-manager.ts:124-137` (`addDelegated`), `src/kit.ts:648-650` (`deployerPublicKey` is a public getter), `src/kit/policies-ops.ts` weighted-threshold signer lists, `createWallet` constructor signers (only WebAuthn today, but `SmartAccountClient.deploy` accepts any `Signer[]`).
- **What:** The seed `"openzeppelin-smart-account-kit"` is public (`constants.ts:91`, `relayer-proxy/src/index.ts:77`). `Delegated(G_shared_deployer)` on any rule means anyone on the internet can satisfy `require_auth_for_args` for that rule. An integrator reading "the deployer authorizes deployments" and seeing `kit.deployerPublicKey` could plausibly add it as a recovery/admin signer. The SDK never warns or refuses.
- **Why it matters:** One line of misuse → total, silent loss of the wallet. The invariant "the shared deployer is never a signer" is stated in `docs/security-deterministic-deployer.md` but not enforced.
- **Rewrite recommendation:** In `validateSigner` (and in the constructor/batch/weighted paths), reject `Delegated(addr)` where `isDefaultDeployer(addr)` with a specific error; also reject `External(*, keyData)` where `keyData` equals the deployer's raw ed25519 key (covers the ed25519 verifier). Do it once, in `auth-core`, on the `Signer` type constructor.

### SEC-F8. Signature expiration is unbounded, and re-signing an already-signed entry silently changes it (invalidating earlier signatures)   [severity: medium]
- **Where:** `src/kit/auth-payload.ts:37-51` (`normalizeSignatureExpirationLedger` accepts anything ≤ `0xffffffff`), `src/kit/webauthn-ops.ts:139-143` (overwrites `signatureExpirationLedger` *before* `readAuthPayload` reads existing signers), `src/kit.ts:454` (`signatureExpirationLedgers` config default 720, no maximum), `src/kit/tx-ops.ts:610` and `:554-560` (`expiration` option passed through untouched), `src/constants.ts:130` (multi-signer uses a different buffer, 100).
- **What:** (a) `kit.sign(tx, {expiration: 4294967295})` or a config of `signatureExpirationLedgers: 10_000_000` is accepted; the host's only cap is the nonce entry's maximum TTL (months, not hours — I did not verify the exact mainnet value offline), so a signed, portable (F1) authorization can live for months. (b) `signAuthEntry` on an entry that already carries an AuthPayload with signers computes a *new* `calculateExpiration()` and writes it into the credentials; the digest of every existing signature was over the old expiration, so they are now invalid, and nothing tells the caller. The multi-signer path avoids this only because it threads one `expiration` through every call.
- **Why it matters:** (a) widens the window for every stolen/portable signature; (b) is a correctness footgun for anyone composing multi-passkey flows from the public `signAuthEntry`.
- **Rewrite recommendation:** In `auth-core`: `expiration` is derived once per signing session and clamped to `min(requested, latest + MAX_SIGNATURE_LIFETIME_LEDGERS)` with a sane default (e.g. 1 day) and an explicit opt-out; if an entry already has signers, the entry's existing `signatureExpirationLedger` *is* the expiration and an override that differs is an error. Same constant for single- and multi-signer paths.

### SEC-F9. `CreateContract` context rules are unreachable through auto-resolution — `buildInvocationContextTypes` throws on every create-contract entry   [severity: medium]
- **Where:** `src/kit/context-rules.ts:102-112, 577-628` (`extractCreateContractWasmHash` probes `createContractHostFn`/`createContractWithCtorHostFn`/`createContractWithConstructorHostFn` and reads `executable.wasm`); the real accessors in stellar-sdk 16.0.1 are `createContractHostFn`, `createContractV2HostFn`, and `ContractExecutable.wasmHash()` (`curr_generated.js:1678-1686, 3159`).
- **What:** Verified empirically: for a V1 entry the function returns `null` → "Unable to extract WASM hash…"; for a V2 entry js-xdr throws "createContractHostFn not set" because the code calls the wrong arm accessor. Consequence: any auth entry where the smart account authorizes a contract creation (the whole purpose of `ContextRuleType::CreateContract`) cannot be signed via `kit.sign`/`signAndSubmit`/`multiSigners` without the caller hand-supplying `contextRuleIds`. No test covers it (`context-rules.test.ts` has zero create-contract cases).
- **Why it matters:** Parity gap with the contract (the brief asks for "everything the contract permits") and dead defensive code that *looks* like it handles the case. Also relevant to F21: the auth_contexts ordering for mixed trees is untested.
- **Rewrite recommendation:** Use the typed accessors directly and fail on unknown arms:
  ```ts
  switch (fn.switch().name) {
    case "sorobanAuthorizedFunctionTypeContractFn": …
    case "sorobanAuthorizedFunctionTypeCreateContractHostFn": exec = fn.createContractHostFn().executable(); break;
    case "sorobanAuthorizedFunctionTypeCreateContractV2HostFn": exec = fn.createContractV2HostFn().executable(); break;
  }
  if (exec.switch().name !== "contractExecutableWasm") throw …; wasm = exec.wasmHash();
  ```
  and add a unit test per arm plus one nested-tree test whose expected `context_rule_ids` order is confirmed against the host (see Open questions).

### SEC-F10. Fresh-device connect assumes `config.defaultPolicies` are the wallet's constructor policies; and the constructor policy map is emitted unsorted   [severity: medium]
- **Where:** `src/kit.ts:1072` (`expectedPolicies: this.defaultPolicies`), `src/kit/wallet-ops.ts:468-472`, `src/kit/wallet-provenance.ts:170-179` (byte-equality against `expectedPoliciesScVal`, which sorts); `src/kit/policies-ops.ts:151-172` (`buildConstructorPolicies` returns an insertion-ordered `Map`), `src/kit/deploy-ops.ts:443-451` → bindings `spec.nativeToScVal` (`contract/spec.js:705-723` copies Map entries in insertion order, no sort).
- **What:** (a) A wallet created with `createWallet(..., {policies: [X]})` or `credentials.deploy(id, {policies})` while `config.defaultPolicies` is `[Y]` (or unset) can never pass `verifyWalletBirth` on a device without the local `birthConstructorArgsHash` — "constructor_mismatch" — so fresh-device recovery is impossible for exactly the wallets that opted into a per-call policy set. The README advertises the per-call override without this caveat. (b) Verified empirically: two constructor policies supplied in non-host order are encoded in that order. Per the host behaviour the `compareScVal` docstring itself cites (`metered_map::from_map` rejects unsorted maps with `InvalidInput`), a multi-policy deploy then only works when the caller happens to list addresses in host order; and regardless of what the host does, `expectedPoliciesScVal` always sorts, so the deploy path and the verification path disagree about what the constructor looks like.
- **Why it matters:** Silent, permanent loss of the recovery path is a security-relevant availability failure; (b) is a plain correctness bug in the deploy path.
- **Rewrite recommendation:** Both vanish under F2 (the address commits to the constructor, so the SDK reads the policies from the birth tx and *presents* them rather than *guessing* them). Short of F2: accept a *set* of acceptable policy configurations at connect, or — better — accept any constructor whose single signer is the passkey and surface the policies to the caller for approval. For (b), `buildConstructorPolicies` must produce entries sorted with `compareScVal` (the same way `buildPoliciesScVal` and `expectedPoliciesScVal` already do) — one helper, three call sites.

### SEC-F11. The trust model is implicit: RPC is fully trusted for state, Horizon's `successful` flag is trusted, and nothing in the types says so   [severity: medium]
- **Where:** `src/kit/wallet-ops.ts:372-392` (current WASM from `getContractData`), `:509-549` (live rule via `readContextRule` simulation), `src/kit/wallet-provenance.ts:205-246` (`getTransaction` status / Horizon `successful`, `ledger_attr`), `src/kit/context-rules.ts:181-224` (rule contents decoded from simulation `retval`), `src/kit.ts:434` (`new RpcServer(config.rpcUrl)` with no `allowHttp` guard beyond stellar-sdk's default).
- **What:** A lying RPC can make the connect path accept a wallet whose code is not on the allowlist, whose rule 0 no longer contains the passkey, or whose birth tx failed; it can also hide/alter rules used for context-rule resolution (F12), and — via F1 — choose what gets signed. Horizon (default `horizon.stellar.org` on mainnet, `kit.ts:472-482`) can only lie about `successful`/`ledger` because the envelope is hash-bound, but that lie is exactly what F2(c) needs. The indexer is the only source the code treats as hostile. None of this is wrong per se — every Stellar client trusts its RPC for *state* — but the SDK's docs promise "fail-closed" and "treat discovery as untrusted" without saying that the RPC URL is a root of trust for both state and (today) signing.
- **Why it matters:** Reviewers and integrators cannot reason about what a compromised dependency buys. E.g. an integrator pointing `rpcUrl` at a free third-party RPC believes they have delegated *reads*; they have actually delegated *what the passkey signs*.
- **Rewrite recommendation:** Encode trust in types: `TrustedRpc` (state reads, simulation *resources*), `UntrustedSimulation` (auth entries — must pass `assertEntryMatchesIntent`), `UntrustedIndexer` (candidates), `UntrustedHistory` (envelopes, hash-bound), `UntrustedRelayer` (hashes, must pass `confirm`). Make `verifyWalletBirth`/`verifyFreshAssertion` pure functions of already-fetched facts so the I/O layer is thin and the verification layer is fuzzable. Document the residual: "RPC is trusted for state; if you want stronger, run your own or diversify (two RPCs must agree on `getContractData`/`getContextRule`)." stellar-sdk already refuses plain `http` RPC URLs without `allowHttp`; apply the same rule to `relayerUrl`/`indexerUrl`/`horizonUrl`.

### SEC-F12. Context-rule auto-resolution is a heuristic over an incomplete, partly indexer-sourced rule list; explicit IDs bypass policies by contract design   [severity: medium]
- **Where:** `src/kit/context-rules.ts:340-428` (`listContextRules`: indexer IDs ∪ probe 0..8 with ≤3 consecutive misses), `:499-575` (`resolveContextRuleIdsForEntry`: single-candidate short-circuit → exact signer-set match → policy-free subset match → throw), `src/kit.ts:1562-1595`, `src/managers/multi-signer-manager.ts:331-344`.
- **What:** (a) Which rules the SDK *sees* depends on the indexer (`getContractDetailsFromIndexer`) and a probe that stops after 3 misses at IDs ≤ 8; a rule with ID ≥ 9 or behind a gap of ≥3 removed IDs is invisible unless the indexer reports it. Rule *contents* come from the RPC, so a hostile indexer can only hide rules, not forge them; hiding a scoped rule with a spending-limit policy makes the resolver pick the Default rule via the `candidates.length === 1` shortcut (`:528-530`) — the policy is skipped. (b) The contract deliberately lets the signer choose the rule (`context_rule_ids` is signer-selected and digest-bound), so a signer present on both a policy-free Default rule and a policy-bearing scoped rule can always pick the weak one by passing `contextRuleIds` explicitly; `preferSpecific` only protects against *accidental* downgrade. (c) The heuristic cannot resolve k-of-n rules when more than one candidate exists (exact match fails, subset match excludes rules with policies → throw), and `candidates.length === 1` returns rules the signer is not even on.
- **Why it matters:** Not a loss-of-funds vector (the rule chosen restricts the *signer's own* action, and the contract enforces the chosen rule), but it is non-deterministic across indexer states, silently weakens policy intent when the indexer is degraded, and is the kind of "magic" an auditor will flag. Integrators who use policies to constrain a *co-signer* must know that the constraint only holds if that co-signer has no policy-free rule for the same context — the SDK does not say so.
- **Rewrite recommendation:** Delete the guessing. Make rule selection explicit and cheap: `kit.rules.candidatesFor(entry, signers) → ContextRule[]` (all matching, with a `why` per rule), and `sign(entry, {ruleIds})` required when `candidates.length > 1`. Keep a convenience for the 90% case: exactly one candidate that contains the signer → auto; otherwise ask. Never let the indexer's *absence* of a rule change the outcome — if the probe/indexer disagree with `get_context_rules_count`, refuse. Document the contract-level fact (b) prominently in the policies guide.

### SEC-F13. A custom `deployerSecret` turns the browser into a hot fee-paying key   [severity: medium]
- **Where:** `src/kit.ts:517-519` (`Keypair.fromSecret(config.deployerSecret)` in the constructor), `src/kit/tx-ops.ts:438-452` (`signFeePayer` signs envelopes with it), `:511-525` (`resolveResimSource` fetches its sequence), README config table.
- **What:** The non-relayer path requires the SDK to hold a funded Stellar secret in page memory and sign every fee-paying envelope with it. Any XSS or malicious dependency drains that account; the SDK offers no signer abstraction for it (the `ExternalSignerManager` exists but is only used for Delegated/Ed25519 wallet signers, not for the fee payer).
- **Why it matters:** The docs steer users to the relayer, but the config option is a first-class field and the demo/README show it. An SDK whose stated goal is "high levels of security" should not have a `secret: string` field in its browser config.
- **Rewrite recommendation:** Replace `deployerSecret` with a `FeePayer` interface (`{ address; signTransaction(xdr) }`), implemented by the relayer, by a SEP-43 wallet, or — for Node/CLI use — by a keypair. If a raw secret must remain, name it `unsafeDeployerSecret` and refuse it when `globalThis.document` exists.

### SEC-F14. WebAuthn signer identification matches on key-data *suffix* with no verifier-address check   [severity: low]
- **Where:** `src/signer-utils.ts:5-17` (`getCredentialIdFromSigner`: any `External` with key data > 65 bytes is "a passkey"), `src/kit/context-rules.ts:441-470` (`findWebAuthnSignerInRules`: first signer whose key data *ends with* the credential ID wins), `:472-497` (`findWebAuthnSignerForCredential`: throws on >1 match), `src/managers/multi-signer-manager.ts:117-125,156-166`.
- **What:** Neither helper checks `signer.values[0] === webauthnVerifierAddress`. A co-signer with add-signer rights can add `External(anyVerifier, junk65 ‖ victimCredentialId)` and (a) make `findWebAuthnSignerInRules` pick the wrong identity (signature then fails on-chain → DoS of the victim's passkey on that rule), (b) make `findWebAuthnSignerForCredential` throw "Multiple WebAuthn signers matched", (c) mis-classify a custom-verifier signer as a passkey in `needsMultiSigner`. No authentication bypass — the AuthPayload maps signer identity → signature and the verifier checks the signature against *that* identity's key.
- **Why it matters:** Cheap DoS by an insider; sloppy identity semantics that a rewrite should not carry.
- **Rewrite recommendation:** A passkey signer is `External(webauthnVerifier, pubkey65 ‖ credentialId)` — match on all three (`signerMatchesCredential` in `wallet-provenance.ts:495-509` already does this correctly; use it everywhere and delete the suffix matchers).

### SEC-F15. `verifyFreshAssertion` takes the expected challenge from the same object as the response; `allowedOrigins` is tautological in-page   [severity: low]
- **Where:** `src/kit/wallet-ops.ts:48-51, 551-575` (`FreshOwnershipProof {response, challenge}` → `expectedChallenge: ownershipProof.challenge`), `src/kit/wallet-provenance.ts:400-411`, `src/kit.ts:462-466` (`allowedOrigins` defaults to `[location.origin]`).
- **What:** The verifier does not own the nonce; whoever constructs the proof object also states which challenge it should match. Inside the SDK both come from `connectWallet`/`authenticateCredential`, so it is safe today, but the shape invites a caller to pass a stale assertion with its own challenge. The origin check compares the browser-supplied origin to a list that defaults to the current origin, so for in-page assertions it can only ever fail through misconfiguration; the meaningful checks are the rpId hash, the challenge, and the signature over the on-chain key (all present).
- **Rewrite recommendation:** `const challenge = verifier.begin(); … verifier.finish(response)` — the verifier stores the challenge (and a short TTL) itself. Keep `allowedOrigins` as an explicit *cross-origin* allowlist only, off by default, and document that the contract does not check origin or rpId (`webauthn.rs:9-15`) so the passkey's security boundary is exactly the rpId scope enforced by the browser: any origin under the rpId (subdomains if rpId is the apex) or any XSS on it can sign for the wallet.

### SEC-F16. WebAuthn `user.id` embeds the user name (PII) and `Math.random`   [severity: nit]
- **Where:** `src/kit/webauthn-ops.ts:79`.
- **What:** `user.id = base64url("${userName}:${ms}:${Math.random()}")`. The spec says the user handle "MUST NOT contain personally identifying information" and it is stored on the authenticator/sync fabric. `Math.random` is the only non-CSPRNG use in the SDK (harmless here).
- **Rewrite recommendation:** `crypto.getRandomValues(new Uint8Array(32))`.

### SEC-F17. Transient RPC failure during connect flips a deployed credential to `"pending"` and throws a plain `Error`   [severity: low]
- **Where:** `src/kit/wallet-ops.ts:372-388`.
- **What:** Any `getContractData` failure (network down, RPC 502) is treated as "not deployed": storage is rewritten to `deploymentStatus: "pending"`, and a generic `Error` is thrown — which `connectWallet`'s restore path does *not* swallow (`:244-254` only catches the three typed errors), so a flaky RPC breaks page load and corrupts local state.
- **Rewrite recommendation:** Distinguish "entry not found" from transport errors; never downgrade stored verification state on a transport error; throw a typed `RpcUnavailableError`.

### SEC-F18. `locallyApproved` is computed from a stored credential that may belong to a different `contractId` than the one being connected   [severity: low]
- **Where:** `src/kit/wallet-ops.ts:345-352, 445-454, 463-467`.
- **What:** When the caller passes both `credentialId` and a `contractId` that differs from `credential.contractId`, `candidateFromStoredCredential` correctly returns `undefined`, but `localPrimary/localSecondary` still read `credential.birthConstructorArgsHash`/`contextRuleId` from the *other* wallet's record and feed them into `verifyWalletBirth` as `expectedConstructorArgsHash`. It fails closed today (hash mismatch), by accident rather than design.
- **Rewrite recommendation:** Scope local approval to the `(credentialId, contractId)` pair; store one record per pair.

### SEC-F19. Deploy path: fee-bumped custom-deployer deployments may disagree about outer vs inner hash across relayer/RPC/Horizon/indexer   [severity: low / open]
- **Where:** `src/kit/deploy-ops.ts:350-370, 377-383` (`sendXdr` → relayer fee-bumps; `confirmSubmittedDeployment` requires `parsed.hash() === hash`), `src/kit/wallet-provenance.ts:255-263`.
- **What:** `TransactionBuilder.fromXDR` of a fee-bump envelope yields a `FeeBumpTransaction` whose `.hash()` is the *outer* hash. If the relayer returns the outer hash and RPC/Horizon index by it, everything lines up; if any party (notably the indexer's `creation_transaction_hash`) records the inner hash, `verifyWalletBirth` fails with `transaction_hash_mismatch` and the wallet is unrecoverable on a fresh device. I could not confirm which hash the OZ channels plugin returns.
- **Rewrite recommendation:** Accept either: compare against `outer.hash()` **or** `inner.hash()` and normalize the stored value to the inner hash (stable across fee bumps). Add an e2e for `deployerSecret` + `relayerUrl`.

### SEC-F20. Relayer proxy nits   [severity: low]
- **Where:** `relayer-proxy/src/index.ts:86-98` (Origin check only when the header is present — it is a browser courtesy, not auth; fine but say so), `:840-857` (testnet friendbot loop keyed on error-message parsing; in `xdr` mode any self-sourced deploy tx from an unfunded account triggers a free friendbot top-up — testnet only), `:867-893` (relayer/plugin error messages are passed through verbatim to clients), `:575-614` (`transfer` on *any* contract is sponsored as long as an allowlisted wallet signs — intentional per the comment, but it means any wallet you deploy for free can then have the relayer pay for calls into arbitrary attacker contracts named `transfer`, bounded only by `MAX_RESOURCE_FEE` and rate limits), `:896-913` (`/status` echoes the caller's IP and key age — harmless).

- **Rewrite recommendation:** Keep it; return a stable machine-readable error code instead of upstream text; consider a per-wallet (not just per-IP) budget since wallets are the real abuse unit.

### SEC-F21. The digest formula is only tested against itself; no cross-implementation vectors; `auth_contexts` ordering for nested trees is an untested assumption   [severity: low]
- **Where:** `src/kit/auth-payload.test.ts:111-126` (recomputes the same formula), `src/kit/context-rules.ts:87-121` (pre-order walk assumed to match the host's `auth_contexts` order).

## Checked and OK

- **Digest preimage:** `buildSignaturePayload` = `sha256(HashIdPreimage)` via stellar-sdk's `buildAuthorizationEntryPreimage` (V1 → `envelopeTypeSorobanAuthorization`, V2/WithDelegates → `…WithAddress`), expiration written into the credentials *before* hashing; `buildAuthDigest` = `sha256(payload ‖ ScVal.scvVec([scvU32…]).toXDR())` — byte-identical to `do_check_auth` (`storage.rs:492-495`, `Vec<u32>::to_xdr` is the `ScVal::Vec` encoding). `computeEntryAuthDigest` is the single formula used by WebAuthn, Ed25519 and Delegated paths.
- **Delegated signer nesting:** `__check_auth(scvBytes(authDigest))` on the account address with V1 credentials and a fresh random nonce matches `addr.require_auth_for_args((auth_digest,))` (`storage.rs:353-356`); AuthPayload entry for the delegate is empty bytes as the contract ignores `sig_data` for `Delegated`.
- **Ed25519:** signs the raw 32-byte digest; verifier calls `ed25519_verify(pubkey, signature_payload, sig)` with `signature_payload = auth_digest` — match. Key/signature sizes asserted.
- **WebAuthn challenge:** `base64url(authDigest)` (43 chars, unpadded) equals `validate_challenge`'s `base64_url_encode(signature_payload[0..32])`; `type` fixed to `webauthn.get` by the browser; `WebAuthnSigData` map keys `authenticator_data < client_data < signature` in host order; `signature` is 64 bytes.
- **DER → compact (`compactSignature`):** SEQUENCE/INTEGER tags, short-form length spanning the buffer, r/s length 1..33, offsets bounds-checked, r and s constrained to `[1, n)`, low-S normalization, 32-byte zero-padding. Handles the leading-`0x00` case. No unbounded reads.
- **Host key ordering (`compareScVal`, `writeAuthPayload`, `buildWebAuthnSignatureBytes`, `buildAddressSignatureScVal`):** type-then-content comparison with Rust slice semantics for Bytes/Symbol/String, XDR-byte compare for Address (discriminant then fixed key) — consistent with host `metered_map` ordering; well documented and tested.
- **`readAuthPayload`/`parseSignerScVal`:** every discriminant checked before access; unknown fields ignored; no throw-on-attacker-bytes beyond typed errors.
- **Nonces/challenges:** `randomAuthEntryNonce` (8 CSPRNG bytes via DataView), `generateChallenge` (32 CSPRNG bytes). Smart-account entry nonces come from simulation (RPC-chosen; reuse is only a tx failure).
- **Re-simulation:** `assembleTransaction` keeps already-present (signed) auth entries; RPC cannot swap them post-signature. Source account for re-sim on the relayer path is a placeholder and the envelope is discarded; direct-RPC path refuses the shared deployer as source (`assertNotSharedDeployerSource`, `resolveResimSource`, `signFeePayer`).
- **Deploy auth entry (`buildDeployTransaction`):** the one place the SDK validates a simulation-returned auth entry — checks the authorized `CreateContractArgsV2` equals the operation's byte-for-byte, deployer address, salt, no sub-invocations; signs with V1 credentials and a 1h expiration. `confirmSubmittedDeployment` re-reads the envelope by hash and requires exactly one matching CreateContractV2.
- **Connect path vs a hostile indexer:** derived address (or explicit `contractId`) is authoritative; indexer candidates are filtered to it; schema-2 completeness/freshness/collision checks; `verifyWalletBirth` binds envelope→hash, create-op→contract ID, WASM→allowlist, constructor→single WebAuthn signer for the configured verifier; the fresh assertion is verified against the key taken from the *birth* (or a locally stored key that was checked against the birth signer), not from the indexer. Then the *live* rule must still contain exactly that `pubkey ‖ credentialId` and be unexpired (`valid_until < ledger` → expired, same inequality as the contract).
- **Fresh assertion (`verifyFreshAssertion`):** credential ID, `type`, challenge, rpId hash (`sha256(rpId)` vs `authenticatorData[0..32]`), UP flag, 65-byte `0x04` key, WebCrypto ECDSA P-256 over `authenticatorData ‖ sha256(clientDataJSON)` — correct per WebAuthn §7.2.
- **Storage contents:** `StoredCredential` and `StoredSession` hold only public data (credential ID, public key, contract ID, hashes, timestamps). A leaked session grants "know which wallet/credential to try", nothing more; signing always requires the authenticator. `ExternalSignerManager` persists only wallet IDs/addresses; keypairs are memory-only and never serialized. No `console.*` prints secrets; error messages never include secrets (`addFromSecret`, `Ed25519Signer.fromSecret` throw generic errors).
- **Prototype pollution / ReDoS / loops:** `JSON.parse` results are only spread into fresh objects (own-property semantics) or iterated via `Object.entries`; all regexes are anchored, linear, and applied to short strings; loops over network data are bounded by tx size, rule-probe config, or indexer counts.
- **Relayer proxy trust boundary:** cannot alter what signed entries authorize; requires exact `func`↔root-invocation equality; refuses source-account auth and sub-invocations; caps fees; rate-limits per IP and globally.

## First-principles recommendations for the rewrite

1. **`auth-core`: one pure module, no I/O, exhaustively tested.** Contents: `signaturePayload(network, entry, expiration)`, `authDigest(payload, ruleIds)`, `encodeAuthPayload/decodeAuthPayload`, `webauthnSigData`, `compactP256`, `hostCompare`, `Signer` constructors with validation (size limits, verifier-specific key shape, **shared-deployer rejection**), `contextsOf(entry)` with correct XDR accessors, `assertEntryMatchesIntent`. ~400 lines. Ship KAT fixtures generated from the Rust tests, property tests for `compactP256` (round-trip against WebCrypto), and a fuzz target for the decoders. Everything else imports from it; nothing else touches `xdr.ScVal` for auth.

2. **Intent-bound signing.** `sign(entry, intent, signer)` is the only way to produce a signature. `Intent` is built by the same function that builds the host function, so the two cannot drift. A signer (`PasskeySigner`, `Ed25519Signer`, `DelegatedSigner`) exposes exactly `signDigest(digest) → bytes` (or, for delegates, `authorizeDigest(digest) → SorobanAuthorizationEntry`). The passkey prompt is preceded by a structured description of the intent that the *app* can render (since the authenticator will not).

3. **Typed trust boundaries.** `TrustedRpc` (state, resources), `UntrustedSimulationAuth`, `UntrustedIndexer`, `UntrustedHistory`, `UntrustedRelayer`. Values that cross a boundary are branded (`Verified<Birth>`, `Confirmed<Submission>`) only by functions in a `verify/` directory that are pure over already-fetched facts. `SmartAccountConfig` requires `https` unless `allowHttp`. Document the residual trust in one table.

4. **Commit the address to the birth.** `salt = sha256(wasmHash ‖ xdr(constructorArgs))`. Delete: `deploymentStatus: "occupied"`, `expectedDeployer/expectedSalt/expectedPolicies`, `sync()`'s occupancy logic, the relayer's constructor-shape check (keep WASM + deployer allowlists), and the `defaultPolicies`↔connect coupling. Keep the shared deployer as a pure namespace key. Fresh-device connect becomes: indexer → candidate → birth tx → `create` args → recompute address → equal? → primary signer is my passkey? → present policies → fresh assertion → live rule check.

5. **Connect path as a pipeline of pure checks.** `connect = fetchFacts(rpc, history, indexer) |> verifyBirth |> verifyCode |> verifyLiveSigner |> verifyOwnership(freshAssertion)`; each step returns a typed result; the I/O adapter is ~50 lines; the verification is ~150 lines and fully unit-testable with fixtures. Scope local approval to `(credentialId, contractId)`. Never mutate storage on transport errors.

6. **Post-submission confirmation for everything.** `confirm(hash, intent) → {ledger, envelope}` used by deploy *and* every op; the relayer is never the source of truth for success.

7. **WebAuthn hygiene.** `userVerification: "required"`, `residentKey: "required"` (make non-discoverable an opt-in with a warning that fresh-device recovery will not work), `user.id` = 32 random bytes, extracted public key validated by WebCrypto import *and* by verifying one assertion before deployment, `rpId` documented as the security boundary.

8. **Expiration policy in one place.** Derived once per signing session, clamped to a configurable max (default ≤ 1 day), never rewritten on an entry that already has signatures; same constant for single- and multi-signer flows.

9. **Explicit rule selection.** `rules.candidatesFor(entry, signers)` + required `ruleIds` when ambiguous; the indexer never influences which rule is signed, only which rules are *listed* for UI. Document the contract-level fact that a signer chooses its rule, so policies constrain a signer only when it has no policy-free rule for that context.

10. **Fee payer as an interface**, not a secret string. Relayer, SEP-43 wallet, or Node keypair implement it; the browser never holds a funded key by default.

11. **Delete or rename the unsafe conveniences:** `addFromSecret`/`addEd25519FromSecret` → `unsafeAddFromSecret` (keep for Node/testing), `sign()` without intent → `signUnchecked()`, `createWallet().contractId` → `predictedContractId` and only after deployment `contractId`.
